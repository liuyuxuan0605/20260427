# MediaPlay / MediaServer 项目开发逐字稿

> 说明：这是以"我是这个项目的开发者"的第一人称视角，把整个 MediaPlay（Windows/Qt 客户端）+ MediaServer（Linux 服务端）项目从 0 到现在的技术选型、架构搭建过程、每个功能模块的实现思路、踩过的坑，完整讲一遍。面试或者复盘的时候可以直接照着这个逐字稿讲。

---

## 一、项目整体是干什么的

这是一个"短视频 + 直播"平台的简化实现，分两端：

- **MediaServer**：跑在 Linux 上的后端服务，纯 C++ 写的，负责用户注册登录、视频上传下载、直播信令、数据落库。
- **MediaPlay**：跑在 Windows 上的 Qt 客户端，负责本地播放器（自研，不依赖 QMediaPlayer）、屏幕/摄像头录制并编码上传、短视频浏览下载、直播推流和拉流观看。

两端之间不用 HTTP，是我自己在 TCP 上定义了一套二进制协议；音视频的编解码、封装、推拉流全部用 FFmpeg 的 C API 直接调，没有用现成的推流 SDK。播放器的音视频同步、画面渲染也是照着 ffplay 的思路自己实现的一套。选这条"平台不给现成的，自己抠"的路线，就是因为这套项目本来的目的是吃透音视频开发的每一个环节，而不是拼凑一个能跑的 demo。

## 二、技术选型：为什么这么选，心路历程

### 2.1 服务端为什么用原生 epoll，而不是用现成的网络库（libevent/muduo/asio）

最开始确实纠结过要不要直接上 muduo 或者 boost::asio，能少写很多样板代码。最后决定自己拿 epoll 撸一遍，原因是：

1. 这个项目的目标是"理解网络编程的底层机制"，如果用别人封装好的 Reactor，我确实能更快出功能，但对"epoll 的 LT/ET 模式区别""EPOLLONESHOT 解决了什么问题""线程池怎么和 epoll 配合"这些问题只能停留在会用层面，回答不出来"为什么"。
2. 这个服务端的并发量级不大（教学/练手项目），性能不是第一优先级，自己写反而能完全掌控每一行代码在干什么，出问题也好排查。

具体设计上：

- `Block_Epoll_Net`（`block_epoll_net.h/cpp`）封装了 epoll 的生命周期：`InitNet` 建监听 socket、设非阻塞、扔进 epoll；`EventLoop` 是标准的 `epoll_wait` 循环，区分 accept 事件和数据到达事件。
- 监听 socket 用 LT（水平触发）模式，因为 LT 简单可靠，漏掉的事件下次 `epoll_wait` 还会通知；ET（边缘触发）虽然效率更高但要求必须一次性把数据读完，容易踩坑，练手项目没必要上 ET。
- 客户端连接的 socket 上监听事件时加了 `EPOLLONESHOT`——这个是关键设计。因为收到数据后我是丢给线程池处理的，如果不加 ONESHOT，同一个 fd 在没处理完这一次数据之前，epoll 又通知了一次，两个线程池线程可能同时处理同一个 socket 的数据，导致收数据的顺序错乱甚至崩溃。加了 ONESHOT 后，这个 fd 处理完一次事件就从监听里摘下来，处理线程干完活后再重新 `eventadd` 挂回去，保证了"同一个连接的数据处理是串行的"，但不同连接之间还是并行的，两全其美。

### 2.2 为什么要自己写线程池，而不是每个连接开一个线程，或者用线程池库

如果每个连接开一个线程（thread-per-connection），实现简单，但连接一多线程数量爆炸，上下文切换开销很大。所以用了"epoll 统一监听 + 线程池处理"的模型：epoll 只负责发现"谁有数据来了"，真正的读数据、业务处理丢给线程池的 worker 线程去干，读事件本身也扔进了线程池（`recv_task`）。

线程池（`Thread_pool.h/cpp`）是生产者-消费者模型的教科书式实现：

- `pool_t` 结构体里一把互斥锁 + 两个条件变量（`not_full` 任务队列没满、`not_empty` 任务队列不空），一个环形数组当任务队列。
- `Producer_add` 是生产者接口，队列满了就 `pthread_cond_wait` 等；`Custom` 是消费者线程主循环，队列空了就等，有任务就取出来跑。
- 加了一个 `Manager` 管理线程，定时检查线程池的忙碌比例，忙碌线程占比超过 80% 或者队列里堆的任务数超过存活线程数就动态扩容线程（在 min~max 之间），忙碌比例太低（小于 1/3）就动态回收线程到 `thread_min`。这一段是仿照实际生产线程池的伸缩策略写的，工程上不算稀奇，但自己实现一遍能真正理解"为什么线程池要有上下限，为什么要动态扩缩容"。

这里有一处我自己设计时留了个注释提醒自己的取舍：`recv_task` 里读数据和处理数据（`Buffer_Deal`）实际上是在同一次线程池任务里顺序执行的，代码里注释掉了"再扔一次线程池"的写法，直接同步调用。这是为了简化，如果要追求极致的"接收"和"处理"解耦，应该是两级线程池，但这样会引入两次任务提交的开销和更复杂的生命周期管理，对这个项目的量级没必要。

### 2.3 为什么自定义二进制协议，而不用 HTTP/JSON 或 Protobuf

三个候选方案：
- HTTP + JSON：通用、好调试，但解析开销大，而且视频文件块传输用 HTTP 每次都要走完整的请求-响应头，效率低。
- Protobuf：工业界标准做法，但引入了额外的依赖和构建复杂度，而且这个项目想让"协议设计"本身成为学习的一部分。
- 自定义二进制协议：4 字节长度头 + 4 字节包类型 + 结构体，`memcpy` 直接读写，效率最高，也逼着自己搞清楚"变长包怎么处理粘包/半包""结构体怎么跨平台对齐"这些问题。

最终选了自定义二进制协议。包格式是：

```
+--------------+------------------+---------------------+
|<-- 4bytes -->|<-- 4bytes类型 -->|<--   业务数据     -->|
+--------------+------------------+---------------------+
|<- packsize ->|<------------ 数据包 struct ------------>|
```

发送端 `SendData` 先把 4 字节的包体长度写进去，再把整个结构体（含类型字段）拼在后面一起发；接收端先 `read` 4 字节拿到长度，再循环 `recv` 直到收满这个长度，天然解决了 TCP 粘包/半包问题——这是自定义二进制协议里最容易出错也最核心的一环，很多人写这种协议会忘记"recv 一次不一定能收满预期字节数"，这里用 `while(nPackSize)` 循环处理，直到收满或者出错。

协议类型用 `_DEF_PACK_BASE = 10000` 起步编号，每一类功能占一段：注册 10000/10001，登录 10002/10003，上传 10004~10006，下载 10007/10008，上传历史 10009/10010，后来加直播又接着往下编 10011~10017。这种"基准值 + 偏移量"的编号方式，好处是加新功能不用改已有编号，客户端服务端两边的 `packdef.h` 保持完全一致的定义即可对上。

服务端用一个函数指针数组做协议分发（`TcpKernel::m_NetPackMap`），`NetPackMap(type)` 宏展开成 `m_NetPackMap[type - _DEF_PACK_BASE]`，O(1) 查到对应的成员函数指针直接调用，不用写一长串 `if/switch`。这是我比较满意的一个小设计，加新协议只需要在 `CLogic::setNetPackMap()` 里加一行映射，不用碰分发逻辑本身。

### 2.4 为什么用 FFmpeg 的 C API 直接编解码，而不用 QMediaPlayer 或者现成的推流 SDK

Qt 自带 `QMediaPlayer`/`QMediaRecorder`，几行代码就能放视频、录像。但这个项目的目的就是要搞懂"播放器内部到底在干什么"——PTS/DTS 是什么、封装格式和编码格式的关系、YUV 和 RGB 怎么转换、音视频同步靠什么机制。用现成播放器控件，这些全部是黑盒。

所以整个客户端的音视频链路——解码播放（`videoplayer.cpp`）、编码录制（`savevideofilethread.cpp`）、摄像头/桌面采集（`picinpic_read.cpp`）、麦克风采集（`audio_read.cpp`）——全部是拿 FFmpeg 4.2.2 的 C API（`avformat_open_input`、`avcodec_send_frame/avcodec_receive_packet`、`sws_scale`、`swr_convert` 这些函数）手写的。渲染用 OpenGL（`myopenglwidget.cpp`）自己上传 YUV/RGB 纹理，没有用 QPainter 画每一帧（那样效率低，CPU 转 GPU 渲染这一步应该交给显卡）。

音频采集是个例外，用了 Qt 的 `QAudioInput`（`audio_read.h`），这里没有再造轮子，因为音频采集本身（从声卡驱动读 PCM）不是这个项目要理解的核心，Qt 的封装够用且跨平台，省下的精力用来搞懂"采集出来的 S16 数据怎么转成 AAC 编码器要的 FLTP 格式"（这块是我们自己用 `SwrContext` 做的，没有走 Qt 的近路）。

### 2.5 为什么最终选 RTMP 做直播/点播传输协议，而不是 HLS 或者裸 TCP 传文件

播放侧最早是纯文件下载（点播下载整个 flv 文件到本地再放），后来切到 RTMP：

- 点播场景，`MediaServer` 存文件、写数据库记 rtmp 路径，播放器直接 `avformat_open_input("rtmp://...")` 边下边播，不用等文件传完。
- 直播场景要解决实时性，RTMP 是这个领域最成熟、FFmpeg 原生支持最好（`rtmp://` 协议是 `libavformat` 内置实现，不需要额外依赖 librtmp）、周边生态最完善（nginx-rtmp-module 现成能用）的方案。相比之下，HLS 有天然的秒级延迟（分片+M3U8刷新），不适合"低延迟直播"；自己写裸 TCP 传输协议要重新解决时间戳、封装格式，等于把 FLV/RTMP 已经解决的问题再造一遍轮子。

所以最终结论是：**推流端**用 FFmpeg 把摄像头/麦克风采集的数据编码成 H.264+AAC，封装成 FLV 格式直接推给 nginx-rtmp；**MediaServer 服务端不转发媒体流**，只负责"谁在直播、直播的 streamKey 是什么"这类信令管理，真正的音视频转发交给专业的 nginx-rtmp 模块去做——这是"专业的事交给专业的组件"的取舍，别自己实现一遍音视频服务器的转发逻辑。

## 三、MediaServer 服务端架构搭建过程

### 3.1 整体分层

```
main.cpp
  → TcpKernel（单例，组合 Block_Epoll_Net + CMysql + CLogic）
      → Block_Epoll_Net   （epoll 事件循环 + 线程池，纯网络层，不懂业务）
      → CMysql             （MySQL 连接封装，加互斥锁保证多线程安全）
      → CLogic             （业务逻辑层，每种协议一个处理函数）
```

这是一个典型的三层架构：网络层不掺杂业务、业务层不管 socket 细节、数据层只管 SQL 执行。`TcpKernel` 是胶水层，把三者串起来，同时提供了协议分发用的函数指针表 `m_NetPackMap`。

`main.cpp` 只有几行：拿 `TcpKernel` 单例、`Open(port)`、`EventLoop()`、退出时 `Close()`。这种"main 函数极简，所有逻辑封装进类"的写法，是为了让程序入口一眼就能看懂整体流程。

### 3.2 数据库层：CMysql

用最原始的 `libmysqlclient` C API（`mysql_init/mysql_real_connect/mysql_query/mysql_store_result`），没有用 ORM 或者连接池。因为：

1. 这个项目是单进程模型，`CMysql` 里只维护一个 `MYSQL*` 连接，靠一把 `pthread_mutex_t` 保护，多个线程池线程共享这一个连接，串行地执行 SQL。这是简化设计——真实生产环境应该用连接池（比如每个线程一个连接，或者 mysqlpp 这类库的连接池），但对这个项目的并发量来说，单连接+互斥锁足够，避免了连接池生命周期管理的复杂度。
2. `SelectMysql` 用 `list<string>` 把结果集摊平成字符串列表返回，调用方按已知的列数手动 `pop_front()` 取值——这是最原始但最直观的做法，牺牲了类型安全换来了实现简单。

这一块如果要往生产级别演进，第一步就是把单连接换成连接池，第二步是把 SQL 拼接换成预编译语句（防注入，见下文"已知问题"部分）。

### 3.3 业务层：CLogic 每加一个功能怎么做的

`CLogic` 的模式很统一：每个协议类型对应一个成员函数，签名都是 `void XxxRq(sock_fd clientfd, char* szbuf, int nlen)`，函数体内部：

1. 把 `szbuf` 强转成对应的请求结构体指针；
2. 按需要查/改 MySQL；
3. 构造回复结构体，通过 `m_tcp->SendData` 发回去。

以注册举例：`RegisterRq` 先查用户名是否已存在，不存在就 `INSERT`，同时在文件系统里给这个用户建一个专属目录（`RootPath + "flv/" + 用户名`），后续这个用户上传的视频都存在自己的目录下——这是"文件系统即索引"的简单设计，不需要单独的目录服务。

上传是分两阶段的协议设计：`UploadRq`（元信息：文件名、大小、用户ID）先建立一条记录，服务端 `fopen` 打开一个文件句柄存进内存 map（`m_mapFileIDToFileInfo`），之后客户端连续发多个 `UploadBlockRq`（每块固定 1024 字节）追加写入，写满或者最后一块小于 1024 字节就判断为传完，关文件、写数据库、回复成功。这种"先声明元信息，再分块流式传输"的协议设计，是文件传输类协议的标准做法，好处是服务端不需要预先知道整个文件多大就能开始接收（虽然这里其实预先知道了，但分块传输本身避免了一次性把整个文件读进内存）。

下载（点播播放列表）是我觉得设计得比较有意思的一块——`GetFileList` 里做了一个简化版推荐算法：

```
前 7 个坑位：按用户勾选的兴趣标签（吃、搞笑、正能量、跳舞、音乐、影视、户外、教育 共 8 个 bool 标签）
           和视频自带的标签做匹配度打分，匹配分高的优先，同分再按热度排序
后 3 个坑位：不看标签匹配度，纯按全站热度倒序
           （目的是避免"信息茧房"——用户标签之外的爆款也要露出）
每次推送过的视频记录进 t_UserRecv 表，下次请求自动排除，全部看完了就清空这张表重新开始推荐
每次曝光（推送成功）给对应视频 hotdegree(热度) +1，形成"越火越推"的滚雪球效应
```

这一段是我在原本"直接按热度倒序取10条"的基础上迭代出来的，加入标签匹配是为了让推荐更贴近个性化，"7+3"的坑位分配是一个简单但有效的"利用（exploit）+探索（explore）"平衡：大部分曝光给用户匹配的内容，留一小部分曝光给全局热门内容防止用户被完全困在自己的兴趣圈子里。

### 3.4 直播功能是怎么从零设计出来的（这是整个项目里最后加的一块，也是设计思路最完整的一次迭代）

这块的设计过程本身很值得讲，因为经历了完整的"方案讨论 → 代码审查发现问题 → 推翻重来"的过程，不是一次写对的。

**第一次讨论：要不要走"服务端中转直播流"的路线**

最开始想的方案是：主播的视频块直接发给 MediaServer，MediaServer 在内存里维护一个"直播间"结构（房间号、主播 fd、观众 fd 列表、最近的关键帧缓冲），主播来一块数据就遍历房间里所有观众 fd 挨个 `send` 转发出去，这是最朴素的"服务器中转"模型。

分析下来这条路会遇到几个硬骨头：
1. 服务端现有的 `DownloadRq` 是"一个连接对应一个文件，阻塞 send 到发完为止"的模型，直播需要的是"一份数据同时发给 N 个观众"，模型完全不一样，不能直接复用。
2. 阻塞 `send` 给多个观众，如果某个观众网络卡了，`send` 阻塞住会拖慢整个转发循环，需要 `SO_SNDTIMEO` 超时兜底，或者干脆给每个观众开独立的发送队列/线程。
3. 新观众加入直播间时，只能从下一个关键帧开始解码（前面提到过的"seek 只能落到关键帧"同样的原理），所以要在房间里缓存最近的关键帧，新观众进来先塞一份关键帧垫底。
4. H.264 一帧数据如果超过协议里固定的传输块大小（1024字节），需要在应用层做"分片-重组"处理。

这几个问题都有解法，但都要往现有的 `Block_Epoll_Net` / `CLogic` 里加不少新东西，属于"服务端自己实现一遍简化版流媒体服务器"的路子。

**第二次决策：改用"客户端直连 nginx-rtmp，服务端只管信令"的方案**

权衡下来最终放弃了服务端中转，理由是：nginx-rtmp-module 这类专业组件已经把"多路推流、多路拉流、GOP缓存补关键帧、断线检测"这些问题解决得非常成熟，自己在 `MediaServer` 里重新实现一遍音视频转发逻辑，工作量大且容易有 bug，性价比不高。**MediaServer 只做一件事：记录"谁在直播、streamKey是什么、状态是不是进行中"，推流和拉流完全交给 nginx-rtmp。**

这个决策直接影响了协议设计：新增的 7 种直播协议包（`_DEF_PACK_LIVE_START/STOP/LIST` 系列）全部是纯信令，不带任何媒体数据，服务端处理函数只做数据库读写（`t_LiveStream` 表：streamId/userId/streamKey/title/startTime/status），不涉及任何 socket 转发逻辑，和现有的注册/登录处理函数是同一种复杂度，不引入新的架构复杂度。

**第三次迭代：客户端怎么接入推流，这里推翻重来了一次**

第一版方案（v1）想的是复用现有的 `RecorderDialog`（录屏功能用的编码类），在 `PlayerDialog` 里再 new 一个 `RecorderDialog` 实例专门做直播推流，靠一个 `m_isRecording/m_isLiveMode` 的互斥标志防止本地录制和直播推流同时跑，抢占同一个 FFmpeg 上下文。

这个方案做代码审查的时候暴露了两个致命问题：

1. **互斥标志设计本身就是错的**——项目里 `UploadDialog` 早就已经持有了一个 `RecorderDialog` 实例（上传视频前先本地录制再上传的流程），如果 `PlayerDialog` 又 new 第二个 `RecorderDialog`，这两个实例各自的 `m_isRecording/m_isLiveMode` 是各自对象的成员变量，**互相看不见**——通过 `UploadDialog` 那条路开始录制，根本不会让 `PlayerDialog` 这条路的互斥标志感知到，互斥形同虚设。这是一个很典型的"以为加了互斥就安全了，但互斥变量的作用域根本没覆盖到真正共享的资源"的错误。
2. **`SaveVideoFileThread` 复用存在线程竞态**——现有代码里 `slot_closeVideo()` 只是把 `isStop` 置成 `true`，从来没有调用 `wait()` 等线程真正退出；而 `slot_setInfo()` 结尾直接 `this->start()` 启动新一轮编码。如果旧的 `run()` 还没退出（可能还在写 `av_write_trailer`、还在 `avformat_free_context` 释放内存），新的 `start()` 已经把 `oc/video_st/audio_st` 这些成员变量覆盖成新的上下文，新旧两个线程同时操作同一批 FFmpeg 对象，轻则花屏，重则直接崩溃。

**最终方案（v2）：直播用全新独立实例，不复用不互斥**

想清楚以后，方案变得很简单：**`LiveDialog` 自己 `new` 一个全新的、独立的 `SaveVideoFileThread` 实例**，跟 `RecorderDialog` 里那个实例毫无关系，各自拥有独立的 `oc/video_st/audio_st`：

- 开播：`new SaveVideoFileThread` → `slot_setInfo(rtmpUrl)` → `slot_openVideo()`，这是全新对象，构造函数里 `isStop` 已经是 `false`，不存在"复用时状态没重置"的问题。
- 停播：`slot_closeVideo()`（置 `isStop=true`，让内部两个 while 循环 drain 完队列）→ **`wait()`**（这是相比 `RecorderDialog` 原有逻辑新增的关键一步，等 `run()` 彻底退出、`av_write_trailer` 和资源释放全部完成）→ `delete`。

这样一来 `RecorderDialog` / `SaveVideoFileThread` 现有代码**一行都不用改**，本地录制功能完全不受影响，直播和录制各自管理自己的编码线程生命周期，从设计上就不存在互斥的必要——这是我更喜欢的解法：**用隔离规避竞态，而不是用锁应对竞态**，隔离的成本（多 new 一个对象）比互斥的成本（要小心翼翼保证锁覆盖了所有共享状态，而且还要处理线程 wait）低得多。

**推流路径为什么不用改 SaveVideoFileThread 一行代码**

`SaveVideoFileThread::slot_setInfo()` 内部调用 `avformat_alloc_output_context2(&oc, NULL, "flv", filename)`，`filename` 传的是 RTMP URL 时，FFmpeg 会自动识别 `rtmp://` 前缀走推流的 IO 路径（`avio_open` 内部分发到 `librtmp` 协议实现），跟传本地文件路径走文件 IO 是完全一样的调用方式，只是 `filename` 变量的内容不同。这是"FLV 容器格式是 RTMP 协议的原生载体"这个事实带来的好处——我们编码时本来就封装成 FLV，直接把输出目标从"本地文件"换成"RTMP URL"，FFmpeg 内部自动切换到网络推流，业务代码完全不用感知这个差异。这一点在正式接入前专门用命令行 `ffmpeg -re -i xxx.mp4 -c copy -f flv rtmp://ip:1935/videotest/test1` 加 `ffplay` 拉流做了实测验证，确认当前项目自带的 FFmpeg 4.2.2 预编译库支持推流这条路径（之前只验证过拉流播放，推流是没验证过的新路径，实测过一遍才敢往生产代码里接）。

**信令和推流怎么串起来（完整数据流）**

主播端：点击"开始直播" → 发 `STRU_LIVE_START_RQ` → 服务端查用户名、生成 `streamKey`（用 `"user_"+用户ID` 保证唯一）、写 `t_LiveStream` 表、回 `STRU_LIVE_START_RS`（带 streamKey）→ 客户端收到成功回复后**才**开始本地推流（`startLivePush`），推流目标地址是拼出来的 `rtmp://ip:1935/videotest/user_5`。

观众端：点"刷新列表" → 发 `STRU_LIVE_LIST_RQ` → 服务端 `JOIN` 查询 `t_LiveStream` 关联用户名表，正在直播的每一条发一个 `STRU_LIVE_LIST_RS` 包，最后发一个 `STRU_LIVE_LIST_END` 收尾（客户端靠这个包知道"列表发完了"，这是处理"一个请求对应多条不定长回复"的标准做法——加一个显式的结束标记，而不是让客户端猜"是不是发完了"）→ 观众选中一条，拼出同样的 RTMP URL，直接扔给现成的 `VideoPlayer` 播放，`VideoPlayer` 本来就能播 `rtmp://` 开头的 URL（因为点播本来就是这么播的），这里直播和点播复用了同一套播放器代码，没有另外写一个"直播播放器"。

停播的顺序也是刻意设计过的：**先停本地推流，再通知服务端**。如果反过来，服务端先把 `status` 改成 0，观众刷新列表已经看不到这路直播了，但主播其实还在推流，nginx-rtmp 那边流还活着，状态不一致（服务端说"没直播"，但流其实还在推）。先停推流让 nginx-rtmp 检测到断流，再改数据库状态，两边保持一致。

**信令包为什么要挂在 OnlineDialog 现有的 TCP 连接上，而不是 LiveDialog 自己开一条新连接**

如果 `LiveDialog` 自己 `new` 一个新的 TCP 连接发直播信令，服务端收到这条连接的包时根本不知道这是哪个用户发的（因为登录状态、`userId → fd` 的映射都是绑定在登录时那条连接上的），等于要在服务端重新走一遍认证流程。所以设计成 `LiveDialog` 复用 `OnlineDialog` 已经登录认证过的那条 TCP 连接：`OnlineDialog` 加一个 `getTcpMediator()` 返回内部的 `m_tcp` 指针（非拥有指针，`LiveDialog` 不负责 delete 它），`PlayerDialog` 构造时把这个指针传给 `LiveDialog::setTcpMediator`。同时 `OnlineDialog` 收到直播相关的回复包时不自己处理，而是 `emit SIG_LivePacket(buf, nlen)` 转发给 `LiveDialog::slot_handleLivePacket` 处理——这是"一条连接，按包类型分发给不同的处理对象"的模式，复用了认证状态，也不需要为每个新功能开新连接。

这里有一个容易踩的坑，专门在设计时理清楚了：`buf` 这块内存的所有权归谁、谁负责 `delete[]`。设计上明确定死：**`buf` 永远由 `OnlineDialog::slot_ReadyData` 函数末尾统一 `delete[]`，`LiveDialog::slot_handleLivePacket` 只读不释放**。这样设计不会有 use-after-free 或者 double-free，前提是 Qt 的信号槽在同一个线程内是 `DirectConnection`（同步调用），`emit SIG_LivePacket` 这一行会阻塞等 `LiveDialog` 的槽函数完全跑完才返回，所以 `LiveDialog` 用完 `buf` 之后 `OnlineDialog` 才执行 `delete[]`，时序上是安全的。如果这两个对象跨线程，Qt 会自动切换成 `QueuedConnection`（异步排队），这个"用完才删"的顺序保证就会失效，需要额外加锁或者拷贝数据——这个项目里因为两个对象都在主线程（UI线程），所以能依赖 `DirectConnection` 的同步语义，这是一个"因为已知的线程模型而可以简化设计"的例子，但如果以后有人把 `LiveDialog` 挪到别的线程，这个假设就会被打破，需要重新审视。

## 四、MediaPlay 客户端架构搭建过程

### 4.1 整体窗口/模块关系

```
PlayerDialog (主窗口，本地播放器)
  ├── VideoPlayer          自研解码播放引擎（FFmpeg解码 + OpenGL渲染 + SDL音频）
  ├── OnlineDialog         短视频浏览/上传/下载模块
  │     ├── LoginDialog     登录注册
  │     ├── UploadDialog    上传视频（内部持有一个 RecorderDialog 用于"录了就传"）
  │     │     └── RecorderDialog  本地录制（摄像头+桌面+麦克风 → 编码 → 存本地文件）
  │     └── TcpClientMediator  客户端网络通信中介
  └── LiveDialog           直播模块（推流开播 + 拉流观看列表）
        └── 自己 new 独立的 SaveVideoFileThread 做推流编码
```

`PlayerDialog` 是最外层窗口，持有播放器和两个功能弹窗（`OnlineDialog`、`LiveDialog`），点按钮弹出对应窗口。这种"主窗口 + 多个功能子对话框"的组织方式，是桌面应用最朴素的做法，没有用更复杂的 MVVM 或者插件化架构，因为整个应用的功能模块数量不多（播放、浏览、直播），朴素分层足够清楚。

### 4.2 播放器：VideoPlayer 是怎么一步步搭起来的

这是整个客户端最核心也最复杂的一块，是照着 ffplay 的经典架构手写的三线程模型：

**第一步：先解决"怎么把压缩文件读出来、分离出音视频流"**

`avformat_open_input` 打开文件（或者 rtmp URL——FFmpeg 对文件和网络流用的是同一套 API，`AVFormatContext` 是"打开的媒体源"这个概念的统一抽象，不用关心它具体是本地文件还是网络流），`avformat_find_stream_info` 探测流信息（有些容器格式头部信息不完整，需要真的读一部分数据才能确定分辨率、采样率），遍历 `pFormatCtx->streams` 找到视频流和音频流各自的索引号。

**第二步：读、解码不能在一个线程里串行做，所以要有队列解耦**

这是这个播放器架构里最重要的设计决策：如果读文件（I/O，速度不稳定）和解码（CPU计算，也需要时间）放在同一个线程里顺序执行，两者会互相拖累——I/O 慢的时候解码线程闲着，解码慢的时点读线程也被卡住，播放会一卡一卡的。

解法是生产者-消费者模型：一个**读线程**专门 `av_read_frame` 读包，按 `stream_index` 分发进两个队列（`videoq`/`audioq`）；**视频解码**在独立的 SDL 线程里跑，从 `videoq` 取包解码；**音频解码**由 SDL 的硬件回调驱动（下面细讲）。`PacketQueue`（`PacketQueue.h/cpp`）就是这个解耦用的队列，本质是一个带互斥锁+条件变量的单向链表，入队 `packet_queue_put` 前必须 `av_dup_packet` 做深拷贝（因为 `av_read_frame` 返回的 packet 内部 data 指针指向 FFmpeg 内部缓冲区，下次读会被覆盖，必须拷贝到独立内存才能安全排队）。

读线程还做了简单的**背压控制**：队列大小超过阈值（视频约 12.7MB，音频约 10MB）就 `SDL_Delay(10)` 暂停读，等消费者线程把队列消耗下去再继续读——这是用"空间换时间"的经典手法，用有限的内存缓冲吸收读写速度差异，避免读太快把内存撑爆。

**第三步：视频线程解码 + YUV转RGB + 上传显示**

视频线程从 `videoq` 非阻塞取包，`avcodec_decode_video2` 解码得到 YUV420P 格式的原始帧（视频压缩存的是 YUV，不是 RGB——这是因为人眼对亮度比对色度敏感得多，YUV420P 的色度分量只有亮度分量 1/4 的数据量，体积只有 RGB24 的一半，这是整个视频压缩行业的基础设计选择，不是这个项目自己发明的）。YUV 转 RGB32 用 `sws_scale`（`SwsContext` 只创建一次，整个播放过程复用，避免重复初始化开销），转出来的 RGB32 数据包装成 `QImage`，**必须** `.copy()` 深拷贝一份再通过信号发给 UI 线程——如果不拷贝直接发，下一帧 `sws_scale` 会把这块内存原地覆盖，UI 线程还没来得及画就已经被改了，这是一个很容易漏掉的坑。

最终渲染没有用 `QPainter::drawImage`，而是自己写了个 `MyOpenGLWidget`（`opengl/myopenglwidget.cpp`），把 RGB 数据当纹理传给 GPU 画。选 OpenGL 而不是 QPainter 的原因是：`QPainter` 每一帧都要 CPU 参与像素级的拷贝和合成，OpenGL 把这部分工作交给 GPU 硬件加速，对视频这种高频率刷新的场景效率明显更高。

**第四步：音频为什么用"回调"驱动而不是像视频那样开个独立线程**

这是这个项目里我觉得最值得讲清楚的一个设计决策。视频线程可以自己控制节奏（想解码就解码，想 sleep 就 sleep），但音频不行——声卡硬件有自己的缓冲区，按固定频率（采样率/缓冲区大小，比如 44100Hz/1024samples ≈ 每 23ms）消耗数据，消耗完就要新数据，如果应用层没跟上就会出杂音或者静音。SDL 提供的模式是"你注册一个回调函数，SDL 内部专门有个线程，声卡需要数据的时候自动调用你的回调"，回调函数（`audio_callback`）只做一件事：把要求的字节数 PCM 数据填进 `stream` 缓冲区。

`audio_decode_frame` 负责实际的解码+格式转换：从 `audioq` 取包，`avcodec_decode_audio4` 解码出 PCM（格式通常是 `AV_SAMPLE_FMT_FLTP`——32位浮点、平面存储，左右声道分开），但 SDL 只认 `AUDIO_S16SYS`（16位整数、交错存储），中间要过一道 `swr_convert` 格式转换。这里有一个我承认但没有立刻修的效率问题：每解码一帧就重新创建一次 `SwrContext`，用完就释放，下一帧再重建——正确做法应该是打开音频流时建一次复用到底，这个项目为了保持逻辑清晰优先做了取舍，性能不是这一块的重点。

**第五步：音视频同步——为什么以音频为主时钟**

这是播放器最核心的原理性问题。三种主时钟方案（音频/视频/外部时钟）里选了音频做主时钟，理由是双重的：
1. 人耳对音频卡顿的感知阈值远低于人眼对丢帧的感知阈值（几十毫秒的音频卡顿能被清楚察觉，但相邻两帧画面的短暂合并显示很难察觉），所以"保音频流畅"优先级更高；
2. 音频输出天然由硬件晶振驱动，回调频率极其稳定，等价于一个高精度的免费时钟，不需要额外维护时钟机制。

具体实现：视频线程在解码下一帧之前，先进入一个比较循环——拿当前 `video_clock`（视频已经解到哪了）和 `audio_clock`（音频已经放到哪了）比较，如果 `video_clock > audio_clock`（视频画面比声音超前），就 `SDL_Delay(5)` 等一会儿再比，直到音频追上来；如果视频已经落后或持平，直接解码显示（这里没有做主动丢帧，落后了就是尽力追赶，会表现为轻微卡顿，这是相对简化的实现，没有像 ffplay 那样做更精细的"差值超过阈值就跳帧"）。

没有音频流的纯视频文件退化成一个更简单的模式：不比较时钟，用 SDL 定时器按帧率算出固定间隔（比如25fps→40ms）定时触发解码显示，这是"没有可靠时钟就退化成尽力而为的定频播放"的兜底方案。

**Seek 跳转为什么必须重置 `video_clock = 0`**

这是同步机制里最容易踩坑也最需要理解清楚的细节。Seek（拖进度条）之后，`av_seek_frame` 只能跳到目标时间之前最近的一个关键帧（因为 P/B 帧依赖关键帧解码，不能凭空从任意时间点开始解码），跳转后读线程往队列里插一个特殊的 FLUSH 包，音视频线程收到 FLUSH 包各自 `avcodec_flush_buffers` 清掉解码器内部状态（防止新旧数据混在一起花屏）。

如果这时候不把 `video_clock` 清零，它还停留在 Seek 前的旧值（比如 300 秒），而音频那边因为解码到了新的关键帧位置，`audio_clock` 已经是新值（比如 60 秒），这样 `video_clock > audio_clock` 这个条件会一直成立，视频线程会卡死在等待循环里出不来，画面冻住。清零后 `video_clock` 几乎肯定小于 `audio_clock`，视频线程能立刻推进。跳转落到的关键帧不一定精确等于目标时间，还需要额外丢弃"关键帧时间点到目标时间点之间"的多余帧，这个逻辑在音视频两个线程里各自都要处理一遍。

### 4.3 录制/编码：SaveVideoFileThread 的设计

这是"反向"的流水线——从采集原始数据到编码压缩写文件。三个协作对象：

- `PicInPic_Read`（视频采集线程）：用 OpenCV 采摄像头，Qt 截屏 API 采桌面，两路可以叠加做画中画效果，采出来是 RGB24，转换成 YUV420P（H.264 编码器只吃 YUV）后发信号扔给编码线程的队列。
- `Audio_Read`（音频采集，注意这个不是 QThread，是普通 QObject 靠定时器驱动）：用 `QAudioInput` 采麦克风得到 S16 PCM，转成 AAC 编码器要求的 FLTP 格式，同样发信号扔进队列。
- `SaveVideoFileThread`（编码线程）：从两个队列里各自取数据，H.264/AAC 编码，`av_interleaved_write_frame` 交错写入 FLV 容器。

编码线程内部用两把独立的 `QMutex`（`m_videoMutex`/`m_audioMutex`）分别保护视频队列和音频队列，采集线程往里塞数据加锁，编码线程往外取数据也加锁，读写双方各自用锁保护，不会有并发问题。

`run()` 主循环的核心逻辑是"谁的下一帧时间戳更靠前就先编谁"：

```cpp
if (视频下一帧的 pts <= 音频下一帧的 pts)
    编码一帧视频
else
    编码一帧音频
```

用 `av_compare_ts` 比较不同 time_base 下的时间戳（视频和音频的编码器 time_base 通常不一样，直接比较数值是错的，必须换算成统一单位再比）。如果视频队列暂时没有新数据（采集慢了），会复用上一帧（`lastVideoNode`）继续编码，保证视频流不断，这是一种简单的容错——牺牲一点精确度换取流的连续性，等新数据来了自然恢复正常。

H.264 编码参数选择上，`preset=superfast` + `tune=zerolatency`：`superfast` 是编码速度优先（因为这是实时采集编码场景，不是离线转码，没有时间给编码器做复杂运算），`zerolatency` 关闭了内部帧缓冲（lookahead）和 B 帧（B 帧需要"看到未来帧"才能编码，天然引入延迟），这是直播/实时传输场景的标准配置。GOP 设为 12（每 12 帧一个关键帧，25fps 下约 0.48 秒一个关键帧），GOP 小意味着关键帧密集，文件稍微大一点，但 seek 更快、断线重连恢复更快——这是"点播/录制可以用大GOP省空间，直播必须用小GOP保证低延迟和快速恢复"这条权衡里，选择了对直播更友好的配置，因为这个 `SaveVideoFileThread` 本身既服务本地录制也服务后来加的直播推流。

线程退出（`slot_closeVideo` 之后）有两段收尾逻辑：先把 `isStop` 置 true，`run()` 里的主循环检测到这个标志并且两个队列都清空了就跳出主循环；然后进入第二段循环，**强制**把队列里剩下的最后一批数据编码写完（不能直接扔一部分数据不编，否则录制的视频结尾会丢帧/丢音）；最后调用 `av_write_trailer` 写文件尾（这一步必须在关闭 codec context 之前做，`av_write_trailer` 可能还要用到编码器的状态信息），依次 `close_stream` 释放两路编码器资源，`avio_closep` 关文件，`avformat_free_context` 释放顶层上下文。这个收尾顺序是有严格依赖关系的，写反了会导致野指针访问或者资源泄漏，这也是为什么直播推流场景下"停播必须 `wait()` 等这一整套收尾流程走完才能 `delete`"——如果不等，新的 `SaveVideoFileThread` 实例的构造/析构和旧实例的收尾逻辑理论上不冲突（因为是独立对象独立资源），但如果错误地想"复用一个实例"，就会撞上这套收尾流程还没走完、新一轮又开始了的竞态，这也是前面直播方案 v1 → v2 迭代要解决的根本问题。

### 4.4 网络通信层：netapi 目录

客户端网络这块做了一层"中介者模式"的封装：`INetMediator`（抽象基类）→ `TcpClientMediator`/`TcpServerMediator`/`UdpMediator`（具体实现），下面再包一层 `TcpClient`/`TcpServer`/`UdpNet` 做真正的 socket 操作。`OnlineDialog`/`LiveDialog` 这些业务代码只认 `TcpClientMediator` 提供的 `SendData`/`OpenNet` 和 `SIG_ReadyData` 信号，不直接碰 socket API——这是典型的"业务层不关心网络细节，只认中介者接口"的封装收益：如果以后要把底层传输换成别的（比如加个自动重连、加个 SSL），只需要改 `TcpClientMediator` 内部实现，业务层代码不用动。

这一层有一个已知但暂时保留的小问题：`TcpClientMediator::SendData` 在重连失败时错误地 `return -1`（函数签名是 `bool`，`-1` 会被隐式转换成 `true`），调用方看到"发送成功"但实际网络没通。这个问题在直播功能设计文档里专门指出过，因为直播场景下这个 bug 的影响被放大了——网络断开重连失败时，主播端以为开播请求发出去了，实际上服务端根本没收到，观众端看列表看不到这路直播，主播还蒙在鼓里。这类"返回值类型和错误码语义不匹配"的 bug 在 C++ 里很容易在 `bool` 函数里习惯性写 `return -1`（受 C 语言"负数表示错误"的老写法影响）而不自知，是代码审查里专门要过一遍的检查点。

### 4.5 直播模块 LiveDialog 的最终形态

已经在服务端那一节详细讲了设计推演过程，客户端侧最终落地的类结构：

- `LiveDialog` 持有一个非拥有的 `TcpClientMediator*`（由 `OnlineDialog` 创建和释放，`LiveDialog` 只是借用，析构时不 delete 它——这种"谁创建谁释放"的所有权约定，在 C++ 里没有智能指针强制的情况下，只能靠注释和代码审查约束，是这类项目里最容易因为"忘记谁拥有谁"而出内存问题的地方，所以专门在头文件注释里标注清楚）。
- 持有一个独立的 `SaveVideoFileThread* m_liveThread`，开播 new，停播 `wait()+delete`，生命周期完全自管理，构造析构成对，不留悬空指针。
- `PictureWidget* m_previewWidget` 主播自己的预览窗口，跟 `RecorderDialog` 的用法完全一致（复制过来的写法，保持项目内同类功能实现方式统一，降低理解成本）。
- `QMap<int, LiveInfo*> m_liveMap` 存直播列表数据，每次刷新前先把上一批 `LiveInfo*` delete 干净再 clear，避免每次刷新都泄漏一批对象。

`PlayerDialog` 的析构函数补充清理 `m_liveDialog`（`delete m_liveDialog`），`LiveDialog` 的析构函数里第一件事是调用 `stopLivePush()`——这保证了即使用户在直播进行中直接关闭整个程序，也会先走完"`wait()` 编码线程退出 → 释放 FFmpeg 上下文 → delete 线程对象"这一整套收尾流程，不会造成线程未退出就被强制析构的资源泄漏或崩溃。这是"析构函数要主动清理自己持有的活跃资源，而不是假设外部一定会先调用停止接口"的防御性设计。

## 五、目前已知但没有修的问题（诚实记录，面试被问到要能讲清楚）

这些问题在代码审查阶段就已经发现，出于不同原因暂时保留，讲项目的时候要能主动提及，体现出"知道问题在哪、为什么先不修"，而不是被问到才支支吾吾：

1. **SQL 注入**：所有 SQL 语句都是 `sprintf` 拼接用户输入直接执行的，没有做参数化查询或者转义。这是最典型的安全问题，没修的原因是这个项目定位是练手/教学项目，没有暴露在公网、没有真实用户数据，但如果要往生产级别演进，这是必须优先解决的一项，应该换成预编译语句（`mysql_stmt_prepare` 系列 API）。
2. **`SaveVideoFileThread::run()` 死循环风险**：如果编码线程因为某种异常一直拿不到"两个队列都为空"的退出条件（比如某一路采集线程卡死不再产生新数据，但也没有真正清空），存在收尾循环空转的可能，这是当前架构里对"异常路径"覆盖不够完整的地方。
3. **服务端 `recv_task` 对半包/断连保护不完整**：内层 `while(nPackSize)` 循环里，如果 `recv` 返回 ≤0（对端断开），当前是直接 `break`，但后续代码没有判断"是不是真的收满了预期字节数"就直接把不完整的缓冲区交给业务层处理，业务层强转结构体指针会读到未初始化或者越界的内存。这个问题在补充直播功能时因为协议数量变多、触发面变大而被重新提出来，修复方案是加一个 `bComplete` 标志，`recv` 提前中断时标记为不完整，直接释放缓冲区走错误处理分支，不进入业务处理。
4. **结构体缺少构造函数导致的栈垃圾问题**：早期定义的协议结构体大多数都写了 `memset(this,0,sizeof(*this))` 的构造函数，但个别字段在极端情况下（比如字符串长度接近缓冲区上限时 `strncpy` 不补 `\0`）仍然可能读到未初始化的栈内存，新增结构体时要求统一带上这个构造函数模式，作为团队编码规范执行。

这些问题没有被"藏起来"，而是作为项目文档的一部分明确写出来，一方面是给未来维护者一个清晰的排雷地图，另一方面这本身也是判断一个人是否真正理解自己写的代码的标准——能准确说出"哪里还有问题、为什么现在没修、修的话思路是什么"，比一个看起来完美但实际没有真正推敲过边界情况的项目更有价值。

## 六、如果重新做一遍，会调整的地方

站在现在回头看，如果这个项目要从教学/练手定位往生产级别演进，会按优先级做这些调整：

1. 服务端 SQL 层先上参数化查询，这是安全底线；MySQL 从单连接+互斥锁换成连接池，提升并发能力。

5. 直播的房间管理如果未来要支持更复杂的场景（比如连麦、弹幕互动），现在"服务端只管信令、媒体流完全交给 nginx-rtmp"的方案会不够用，需要重新评估要不要引入类似 SRS（Simple Realtime Server）这类更专业的流媒体服务器，或者在应用层补一层信令服务器专门处理低延迟互动数据（这块目前没做，也不在当前版本范围内）。

## 七、直播完整链路串讲：从摄像头到观众端

前面第三、四节是分模块讲的，这里把直播场景下数据怎么从主播摄像头一路流到观众屏幕，串成一条完整链路：

```
【主播端】

                                 │ sws_scale (RGB24→YUV420P)

              │ swr_convert (S16→FLTP)│

        H.264编码(视频)        AAC编码(音频)

                    (FLV容器交错写入)
```

关键设计点复述一遍：**服务端只管信令（谁在播、streamKey是什么），不碰媒体流一个字节**，真正的音视频转发/GOP缓存/多路分发全部交给 nginx-rtmp 这类专业组件承担，这是第三节"直播功能设计推演"里权衡出来的结论。

### 7.1 RGB、YUV、H.264 的区别和实际效果

这三者容易被并列误解成"三选一的格式"，实际上是数据在链路上的**三个不同阶段**，不是同层面的东西：

| | 是什么 | 谁在用 | 体积（1920×1080一帧） |
|---|---|---|---|
| **RGB** | 每个像素存 R/G/B 三份完整数值 | 显示器/GPU渲染、摄像头原始输出 | 宽×高×3 字节 ≈ 6MB |
| **YUV(420P)** | 亮度(Y)+色度(U/V)分离，色度降采样 | 编解码器的原生工作格式 | 宽×高×1.5 字节 ≈ 3MB |
| **H.264** | 一种**压缩算法**，不是像素格式 | 存储/网络传输的最终形态 | 同样内容几百KB~几Mbps |

**RGB→YUV 为什么要转、效果差在哪**：人眼对亮度变化极敏感，对色度变化相对迟钝。YUV420P 利用这个生理特点，每 4 个像素的 Y（亮度）全部保留，但共用 1 组 U/V（色度），体积直接砍掉一半，主观画质几乎无损失。这是编码前必须做的"减法"，项目里 `sws_scale` 在采集端做 RGB24→YUV420P、播放端反过来做 YUV420P→RGB32（渲染要用），两个方向都是同一个函数，只是参数反过来。

**H.264 和前两者本质不同**：RGB/YUV 都是**原始像素数据**，没有压缩，画质无损但体积大到没法传输存储（一部两小时电影按 YUV 存要 1TB+）。H.264 通过帧内预测（I帧，独立解码）+帧间预测（P/B帧，只存和参考帧的差异）+变换量化+熵编码，把几 MB 的原始帧压缩到几十 KB，压缩比几十到几百倍，代价是**有损**——码率越低损失越明显。这也是为什么项目里编码参数要按场景调（直播用 `superfast+tune=zerolatency` 保证低延迟，牺牲一部分压缩效率；GOP=12 让关键帧更密，断线重连恢复快，代价是文件体积比大 GOP 略大）。

一句话总结：**RGB 是给人眼看的，YUV 是给编码器用的中间态，H.264 是给网络和硬盘用的压缩态**，三者卡在"摄像头→编码→传输→解码→显示"链路的不同位置，不能互相替代。

### 7.2 大文件分片上传的网络自适应策略（现状 vs 改进建议）

> ⚠️ 这一小节和前面几节性质不同：前面是对**现有代码**的描述，这里是**现状问题 + 尚未实现的改进建议**，两者不要混为一谈。

**现状**：`onlinedialog.cpp` 里的 `UploadFile` 是这样写的：

```cpp
while(1){
    STRU_FILEBLOCK_RQ blockrq;
    int64_t res = fi.pFile->read(blockrq.m_szFileContent, _DEF_CONTENT_SIZE); // 固定1024字节
    ...
    m_tcp->SendData(0, (char*)&blockrq, sizeof(blockrq));  // 同步阻塞发送，发完立刻发下一块
    ...
}
```

固定 1024 字节分片、完全串行、没有重试、没有断点续传、失败了也不感知——这个 1024 字节的分片大小是从协议里 `_DEF_CONTENT_SIZE` 复用过来的（原本是为了跟播放器那边"固定块传输"的设计保持一致），并不是为上传网络场景专门设计和优化过的。这套在教学项目里够用，但如果要支撑"不同网络场景下的上传"，需要补上下面这些：

**1）分片大小应按网络质量动态调**：1024 字节对文件上传来说偏小，分片越小协议头开销占比越高。合理策略是分片大小跟着链路质量走——WiFi/有线网调大到 256KB~1MB，减少分片数量；4G/5G 用中等分片（如 256KB），兼顾吞吐和失败重传成本；弱网（信号差、2G/3G）调小到 64KB 甚至更小，单片传输时间短，一旦超时/失败重传代价小，不会因为一片很大的数据反复失败卡死整个上传。

**2）并发度要自适应**：现在是完全串行，一片发完立刻发下一片（连"等确认"都没有，是发了就当成功的乐观写法）。真正的上传优化应该像分片上传协议那样开多个并发连接同时传：强网开 4~8 个并发，弱网限制到 1~2 个（并发太多在弱网下反而互相抢带宽，单片成功率更低）。可以用一个简单的滑动窗口，根据最近几个分片的实际耗时动态调整并发数，类似 TCP 拥塞窗口的思路。

**3）断点续传**：目前协议里分片没有序号字段，靠发送顺序和服务端 FIFO 处理隐式对应，一断线整个上传作废。要支持断点续传，协议要加一个 `m_nBlockIndex` 分片序号字段，服务端按 `fseek` 到对应偏移量落盘而不是永远 `fwrite` 追加，客户端重连后先问服务端"这个文件已经收到多少字节了"，从那个位置继续读文件发送。这个改造也是支持"并发乱序到达"的前提——现在协议假设分片严格按顺序到达，一旦允许并发发送，后发的片可能先到，服务端没有序号字段就没法正确定位落盘偏移。

**4）失败重试要有退避机制**：现在 `SendData` 失败没有任何重试逻辑（下载路径判断了 `ret < 0` 就 `break`，上传路径连这个判断都没有）。合理做法是单片失败后指数退避重试几次（如 500ms、1s、2s），超过阈值判定链路暂时不可用，暂停整体上传等网络恢复，而不是直接判上传失败——移动网络下信号短暂丢失几秒很常见，不应该直接导致整个上传失败。

**5）服务端要有流控反馈，不能只靠 TCP 自身**：项目里播放器读线程已经有"队列超过阈值就暂停读"的背压设计（`videoplayer.cpp` 里 `MAX_AUDIO_SIZE`/`MAX_VIDEO_SIZE` 那段），但上传方向完全没有对应机制——服务端写文件慢或数据库压力大时，客户端完全感知不到，只能一直发，靠 TCP 自身滑动窗口硬扛。更好的做法是应用层加一个简单的 ACK/窗口机制，服务端处理不过来时明确告知客户端"慢一点"，客户端据此降低并发或暂停发送。

**6）结合业务场景的产品级策略**：既然是短视频上传场景，可以在弱网下做得更主动——检测到当前是移动网络或信号差，给用户一个选项"检测到网络较差，是否压缩后上传"或"仅 WiFi 时上传"，把控制权交给用户，而不是硬扛着传一个可能传半天传不完的原始大文件。

**改造优先级**：把现在"固定 1024 字节串行发送"改造成真正能适应不同网络场景的上传方案，第一步是给协议加分片序号（这是支持并发和断点续传的前提），第二步是加失败重试和超时判定，第三步才是根据网络质量动态调分片大小和并发数——前两步是"能用"，第三步是"好用"，顺序不能颠倒。

## 一、最基础的几组概念辨析

### 1.1 容器格式 vs 编码格式——两个经常被混为一谈的概念

- **编码格式（Codec）**：一种压缩算法，规定"数据怎么被压缩、怎么被还原"，比如 H.264（视频压缩算法）、AAC（音频压缩算法）。
- **容器格式（Container）**：一个"打包箱"，负责把已经压缩好的视频数据、音频数据、时间信息、字幕等打包在一起，并在文件头记录"里面装的是什么编码"，比如 MP4、FLV、MKV、TS。

项目里两者的关系体现得很清楚：`savevideofilethread.cpp:419`

```cpp
avformat_alloc_output_context2(&oc, NULL, "flv", filename); // 容器格式=flv
add_video_stream(&video_st, oc, &video_codec, AV_CODEC_ID_H264); // 视频编码=H.264
add_audio_stream(&audio_st, oc, &audio_codec, AV_CODEC_ID_AAC);  // 音频编码=AAC
```

**FLV 容器 + H.264/AAC 编码，这个组合不是随便选的**——FLV 是 RTMP 协议的原生载体格式，两者天然绑定，这也是为什么项目里录制和直播用同一个 `SaveVideoFileThread`：只要把输出目标从本地文件路径换成 `rtmp://` URL，FFmpeg 通过 `avio_open` 自动识别协议前缀走推流，容器格式不用换，业务代码不用改一行（详见"三、RTMP 推拉流"一节）。

### 1.2 AVPacket（包）和 AVFrame（帧）的区别

这是 FFmpeg 编程里最容易搞混的一对概念：

- **AVPacket**：从文件/网络读出来的**压缩数据片段**，还没解码，不能直接用。一个视频 packet 通常对应一个编码帧；一个音频 packet 可能包含多个编码帧。
- **AVFrame**：解码器处理 packet 之后输出的**原始数据**。视频 frame 是 YUV 像素数据，音频 frame 是 PCM 采样数据。

数据流向：`文件 → Packet(压缩态) → 解码 → Frame(原始态) → 播放`。

项目里 `videoplayer.cpp` 的 `video_thread` 函数完整体现了这条链路：`packet_queue_get` 从队列取出 `AVPacket`，`avcodec_decode_video2(pCodecCtx, pFrame, &got_picture, packet)` 解码成 `AVFrame`（`pFrame`），再 `sws_scale` 转换格式给显示用。

### 1.3 编码/解码的方向

- **编码（Encode）**：原始数据 → 压缩数据。项目里 `savevideofilethread.cpp` 的 `write_video_frame`/`write_audio_frame`，核心 API 是 `avcodec_send_frame` + `avcodec_receive_packet`。
- **解码（Decode）**：压缩数据 → 原始数据。项目里 `videoplayer.cpp` 的 `video_thread`/`audio_decode_frame`，核心 API 是 `avcodec_decode_video2`/`avcodec_decode_audio4`（这是 FFmpeg 3.x 之前的旧 API，项目用的 FFmpeg 4.2.2 里这套 API 还能用但已标记 deprecated，新项目应该统一改用 `avcodec_send_packet`+`avcodec_receive_frame`）。

一套完整项目里，编码和解码几乎是镜像对称的两条流水线，理解一条另一条基本能反着推出来。

## 二、色彩空间与图像格式：RGB / YUV

### 2.1 为什么要有 YUV，不能全程用 RGB 吗

- **RGB**：每个像素存 R/G/B 三份完整数值，是显示器渲染、摄像头原始输出、GPU 纹理使用的格式。
- **YUV**：把亮度（Y）和色度（U/V）分离的颜色模型，是编解码器的原生工作格式。

选择 YUV 的根本原因是人眼生理特性：人眼对**亮度**变化极敏感，对**色度**变化相对迟钝。YUV420P（"420"表示色度分量在水平和垂直方向都做 2x 降采样，即每 4 个 Y 像素共用 1 组 U/V）利用这一点，在几乎不损失主观画质的前提下把数据量砍掉一半：

```
RGB24： 宽×高×3 字节
YUV420P：宽×高×1.5 字节  （只有 RGB24 的一半）
```

H.264/H.265 等所有主流视频编码标准都是基于 YUV 设计的，编码器不认 RGB，所以**摄像头采集的 RGB 数据在送进编码器之前必须先转成 YUV**；播放时反过来，解码器吐出来的是 YUV，屏幕显示需要 RGB，还要转回去。这一"来回转换"是整条音视频链路里最基础也是发生频率最高的操作。

### 2.2 项目里两次方向相反的转换，用的是同一个函数

**采集侧（RGB→YUV）**，`picinpic_read.cpp:89` 的 `ImageToYuvBuffer`：

```cpp
SwsContext *rgb_to_yuv_ctx = sws_getContext(w, h, AV_PIX_FMT_RGB24,
                             w, h, AV_PIX_FMT_YUV420P,
                             SWS_BICUBIC, NULL, NULL, NULL);
sws_scale(rgb_to_yuv_ctx, pFrameRGB->data, pFrameRGB->linesize, 0, h,
          pFrameYUV->data, pFrameYUV->linesize);
// 转换完之后手动拼接 Y、U、V 三个平面到一块连续内存
memcpy(picture_buf, pFrameYUV->data[0], y_size);              // Y 平面，全尺寸
memcpy(picture_buf+y_size, pFrameYUV->data[1], y_size/4);     // U 平面，1/4尺寸
memcpy(picture_buf+y_size+y_size/4, pFrameYUV->data[2], y_size/4); // V 平面，1/4尺寸
```

这里能看出 YUV420P 的内存布局是三个独立平面顺序排列，Y 平面大小是 U/V 平面的 4 倍，这就是"420"的具体体现。

**解码播放侧（YUV→RGB）**，`decode_pipeline.md` 里讲解过、代码在 `videoplayer.cpp`：

```cpp
img_convert_ctx = sws_getContext(width, height, pCodecCtx->pix_fmt,     // 输入YUV
                                  width, height, AV_PIX_FMT_RGB32,      // 输出RGB32
                                  SWS_BICUBIC, NULL, NULL, NULL);
sws_scale(img_convert_ctx, pFrame->data, pFrame->linesize, 0, height,
          pFrameRGB->data, pFrameRGB->linesize);
```

两处用的都是 `SwsContext` + `sws_scale`，只是参数方向相反——`SwsContext` 本质是一个通用的图像格式转换器，不只能转 YUV/RGB，任意两种 FFmpeg 支持的像素格式之间都能转，缩放（改变宽高）也是同一个函数做的（`SCALE_FLAGS`/`SWS_BICUBIC` 是插值算法，这里两处场景都没有真正缩放尺寸，只做格式转换，但函数本身是通用的）。

**为什么目标格式选 RGB32 而不是 RGB24**：`common.h` 没有直接体现但 `decode_pipeline.md` 里解释过——Qt 的 `QImage::Format_RGB32` 直接对应这个格式，不需要额外转换就能包成 QImage；而且 4 字节对齐的内存访问效率比 3 字节的 RGB24 更高。

### 2.3 一个容易忽略的坑：QImage 只是"视图"，不拥有数据

`sws_scale` 转换完的数据存在 `out_buffer_rgb` 里，如果直接：

```cpp
QImage tmpImg((uchar*)out_buffer_rgb, width, height, QImage::Format_RGB32);
emit SendGetOneImage(tmpImg);  // 错误！
```

`tmpImg` 只是对 `out_buffer_rgb` 这块内存的一个包装视图，并不拥有这块内存。下一帧 `sws_scale` 会原地覆盖 `out_buffer_rgb`，如果 UI 线程还没来得及画完上一帧，数据已经被换成下一帧的了。项目里的正确写法是显式 `.copy()` 做深拷贝：

```cpp
QImage image = tmpImg.copy();
is->m_player->SendGetOneImage(image);
```

这是"谁拥有这块内存、生命周期到哪"这个问题在图像处理里的一个典型体现，贯穿整个项目（`buf` 的所有权问题在直播模块的 `OnlineDialog`/`LiveDialog` 之间也出现过一次，思路是一样的）。

## 三、视频压缩的核心机制：H.264 / GOP / 帧类型

### 3.1 H.264 和 RGB/YUV 不是同一层面的东西

RGB/YUV 是**未压缩的像素数据格式**，H.264 是**压缩算法**。三者在链路上的位置：

```
摄像头 → RGB(原始，~6MB/帧 1080p) → YUV420P(原始，~3MB/帧) → H.264编码(压缩，几十KB/帧)
```

H.264 通过帧内预测（I帧）+帧间预测（P/B帧）+变换量化+熵编码，把 YUV 数据压缩几十到几百倍，代价是**有损**——这也是为什么编码参数要按场景权衡（下面细讲）。

### 3.2 I帧、P帧、B帧

- **I帧（关键帧）**：完整存储一帧画面，不依赖其他帧，可独立解码。
- **P帧（预测帧）**：只存与前一帧的差异，体积小，解码依赖前面的帧。
- **B帧（双向预测帧）**：参考前后两帧做差，压缩率最高，但解码顺序（DTS）早于显示顺序（PTS），引入延迟。

项目里 `uploaddialog.cpp:150` 生成视频缩略图时，专门筛选关键帧来截图：

```cpp
if (got_picture && pFrame->key_frame == 1 && pFrame->pict_type == AV_PICTURE_TYPE_I) {
    // 只有关键帧的画面是完整的，可以直接转成缩略图
}
```

这是"利用 I 帧可独立解码"这个特性的直接应用——不需要从头顺序解码整个视频，跳着找到几个 I 帧就能各自独立还原出完整画面。

### 3.3 GOP（Group of Pictures）

GOP 是两个相邻 I 帧之间的帧数。项目里 `savevideofilethread.cpp:293`：

```cpp
c->gop_size = 12; /* emit one intra frame every twelve frames at most */
```

帧率 25fps，GOP=12，意味着每 0.48 秒一个关键帧。GOP 大小的权衡：

| GOP | 文件体积 | Seek/断线重连速度 | 适用场景 |
|---|---|---|---|
| 大（如250） | 小（I帧少） | 慢（要找最近I帧才能开始解码） | 点播/存档 |
| 小（如12） | 略大（I帧多） | 快 | 直播、录屏、需要精确定位的场景 |

项目里录制和直播用的是同一个 `SaveVideoFileThread`，GOP 统一设为 12——这个配置对直播更友好（快速恢复），录制场景牺牲了一点点存储效率，是"一套代码两个场景复用"下的权衡取舍。

### 3.4 编码参数：preset 和 tune

`savevideofilethread.cpp:372`：

```cpp
av_dict_set(&opt, "preset", "superfast", 0);
av_dict_set(&opt, "tune", "zerolatency", 0);
c->thread_count = 4;
```

- **preset**（速度预设）：从 `ultrafast` 到 `veryslow`，越慢压缩率越高、文件越小，但 CPU 占用越大。项目选 `superfast`，因为这是实时采集编码场景（摄像头/桌面实时录制/推流），速度优先，不能像离线转码那样慢慢压。
- **tune**（场景调优）：`zerolatency` 关闭编码器内部的帧缓冲（lookahead）和 B 帧——B 帧需要"看到未来帧"才能编码，天然引入延迟，直播/实时传输场景必须关掉。
- `thread_count=4` 开 4 个 CPU 线程并行跑软编码，压榨多核性能。

**录制 vs 直播在编码策略上的理论差异**（项目里两者复用同一套参数，这是权衡后的简化，工程上更精细的做法应该按场景区分）：

| 对比项 | 录制文件 | 直播推流 |
|---|---|---|
| 延迟要求 | 无要求 | 越低越好（<3s） |
| preset | slow/medium，画质优先 | superfast，速度优先 |
| B帧 | 可以用 | 禁用（zerolatency） |
| GOP | 可以大 | 1~3秒，方便断线重连 |
| 输出 | MP4/MKV，可seek | RTMP/FLV，流式 |

## 四、音频基础：PCM / 采样率 / 采样格式 / 声道

### 4.1 PCM 是什么

PCM（脉冲编码调制）是未压缩的原始音频，把声音振幅按固定频率采样成数字序列，是音频世界里"YUV/RGB"对应的原始数据形态。

### 4.2 采样率、采样精度、声道数——决定原始数据量的三要素

项目里 `audio_read.h` 的常量定义：

```cpp
#define AudioCollectFrequency (44100)   // 采样率 44.1kHz
#define AudioChannelCount (2)            // 双声道
// QAudioFormat 设置 setSampleSize(16)   // 16位采样精度
```

数据量计算方式：`采样率 × 采样精度(字节) × 声道数 = 每秒数据量`。项目注释里写得很直白：

```
单通道 16位 一次采样 2字节，双通道 16位 一次采样 4字节
aac 数据是一帧 1024 采样点，ffmpeg 使用 fltp 是 float，一个点双声道*2 就是*8 即 8192字节
```

### 4.3 采样格式转换：S16 → FLTP，为什么必须转

- **S16**：16位有符号整数，交错存储（左右声道交替：`LRLRLRLR`），麦克风/声卡最常见的原始格式，`QAudioInput` 采出来就是这个。
- **FLTP**：32位浮点数，平面存储（左右声道分开：`LLLL...RRRR...`），AAC 编码器内部要求这个格式。

项目 `audio_read.cpp:180` 的转换配置：

```cpp
in_sample_fmt = AV_SAMPLE_FMT_S16;      // 输入：S16交错
out_sample_fmt = AV_SAMPLE_FMT_FLTP;    // 输出：FLTP平面
swr = swr_alloc_set_opts(nullptr, out_ch_layout, out_sample_fmt, out_sample_rate,
                          in_ch_layout, in_sample_fmt, in_sample_rate, 0, nullptr);
swr_init(swr);
```

`swr_convert` 真正执行转换，输出的 `out_buffer[0]`/`out_buffer[1]` 分别是左右声道数据，之后再手动拼接成 FLTP 要求的"先左声道全部、再右声道全部"的内存布局（`audio_read.cpp:122-129`）。

`SwrContext`（音频）和 `SwsContext`（视频/图像）是一对概念：**Swr = SoftWare Resample（重采样），Swr 用 `swr_convert`；Sws = SoftWare Scale（缩放/转换），Sws 用 `sws_scale`**。一个管音频格式/采样率转换，一个管视频像素格式/尺寸转换，项目里两者分别在音频链路和视频链路上各自扮演"格式适配层"的角色。

### 4.4 为什么音频帧固定是 1024 个采样点

AAC 编码器的工作单元固定是 1024 个采样点（AAC 标准规定，基于 MDCT 变换块大小）。项目注释算过这个时间关系：

```
48kHz : 1000 = 1024 : x   → x ≈ 21.3ms，取整为 20ms 采样间隔
44100Hz 下，1024点约等于 23.2ms
```

`audio_read.h` 里 `#define AUDIO_INTERVAL (20)` 就是照这个算出来的采集定时器间隔。

### 4.5 音频采集为什么用定时器轮询，视频解码为什么用独立线程

这是一组值得对比的设计：视频解码线程（`video_thread`）可以自己控制节奏，想解码就解码，想 sleep 就 sleep；但音频播放侧必须由 SDL 硬件回调驱动（下面第五节细讲），而**音频采集侧**（`Audio_Read`）项目选择了用 `QTimer` 定时轮询 `audio_in->bytesReady()`，而不是开一个独立线程——因为采集这一端不需要严格卡在硬件时钟上，只要保证"数据攒够一批就处理"即可，用定时器实现简单，避免了额外的线程同步开销。这体现了"采集端可以宽松，播放端必须精确对齐硬件节奏"的不同要求。

## 五、音视频同步

### 5.1 三种同步策略

| 策略 | 主时钟 | 优点 | 缺点 |
|---|---|---|---|
| 以音频为主 | 音频PTS | 感知最准，人耳对声音延迟极敏感 | 视频需丢帧/等待 |
| 以视频为主 | 视频PTS | 画面流畅无跳帧 | 音频可能卡顿/加速 |
| 以外部时钟为主 | 系统时钟 | 解耦音视频，适合网络直播 | 实现复杂，需主动纠偏 |

**项目本地播放器用音频为主时钟**，理由有二：人耳对音频不连续的感知阈值远低于人眼对丢帧的感知阈值；音频输出由声卡硬件驱动，天然是一个稳定的高精度时钟，不需要额外维护。

**直播场景理论上更适合外部（墙钟）时钟**——网络抖动会让 `audio_clock` 停滞，以它为主会让视频画面也跟着卡住；用系统时钟让播放速度和真实时间绑定，配合抖动缓冲区独立吸收网络抖动，更稳健。这一点项目当前的直播实现（直接把点播用的 `VideoPlayer` 拿来拉流播放）复用的是同一套"音频为主时钟"逻辑，属于工程上"先用现成的能力跑通功能"的简化，如果要精细化优化直播观感（弱网下减少卡顿），下一步应该考虑针对直播场景引入外部时钟或抖动缓冲。

### 5.2 具体同步实现：视频主动等音频

`videoplayer.cpp:99-115` 核心同步循环：

```cpp
while (1) {
    if (is->quit) break;
    if (is->audioq->size == 0) break;    // 音频队列空了就别等，防止死等
    audio_pts = is->audio_clock;
    video_pts = is->video_clock;
    if (video_pts <= audio_pts) break;   // 视频没超前，可以显示
    SDL_Delay(5);                        // 视频超前了，睡5ms再看
}
```

`video_clock` 每帧解码后由 `synchronize_video` 更新（处理无 PTS 和 `repeat_pict` 重复帧两种情况）；`audio_clock` 在每次成功解码一帧音频后更新（`videoplayer.cpp:732`：`audio_clock = pkt.pts * av_q2d(time_base) * 1000000`）。

### 5.3 编码端也有一次同步，逻辑相反

播放端是"视频等音频"，**编码端**（`savevideofilethread.cpp` 的 `run()`）反过来是"谁的时间戳早就先编谁"：

```cpp
if (!have_audio || av_compare_ts(video_st.next_pts, video_st.enc->time_base,
                                   audio_st.next_pts, audio_st.enc->time_base) <= 0)
    write_video_frame(...);
else
    write_audio_frame(...);
```

这里用 `av_compare_ts` 而不是直接比较数值，是因为音频和视频的 `time_base`（时间基）通常不同（音频常见 `{1, 44100}`，视频常见 `{1, 25}`），直接比较毫无意义，必须换算成统一的时间刻度再比。**`time_base` 是贯穿整个 FFmpeg 编解码 API 的核心概念**：`pts × time_base = 实际时间（秒）`，写文件前要用 `av_packet_rescale_ts` 把 packet 的时间戳从编码器 time_base 转换成流的 time_base，否则播放时间会全错。

### 5.4 Seek 跳转后为什么要重置 video_clock

Seek 只能跳到目标时间之前最近的关键帧（`av_seek_frame(..., AVSEEK_FLAG_BACKWARD)`），跳转后：

1. 清空音视频队列，塞一个 FLUSH 特殊包；
2. 音视频线程收到 FLUSH，`avcodec_flush_buffers` 清解码器内部缓存（防止新旧帧混着解码导致花屏），**同时 `video_clock = 0`**；
3. 各自丢弃"关键帧时间点"到"目标时间点"之间的多余帧。

**为什么必须清零 `video_clock`**：如果不清零，它还停留在跳转前的旧值（比如300秒），而音频侧因为已经从新关键帧位置重新更新了 `audio_clock`（比如60秒），`video_clock(300) > audio_clock(60)` 这个条件会一直成立，视频线程会在等待循环里死等，画面冻结。清零后 `video_clock` 几乎肯定小于新的 `audio_clock`，视频线程立刻能推进——这是整个同步机制里最容易被问到、也最能考察是否真正理解同步原理的一个细节。

## 六、生产者-消费者模型：贯穿全项目的核心并发模式

项目里几乎所有"数据从一个环节流向下一个环节"的地方都用了这个模式，值得单独列出来对比：

| 场景 | 生产者 | 消费者 | 队列/缓冲 | 同步原语 |
|---|---|---|---|---|
| 播放-解封装 | 读线程(av_read_frame) | 视频/音频解码线程 | `PacketQueue`(单向链表) | SDL_mutex + SDL_cond |
| 录制-编码 | 摄像头/麦克风采集线程 | SaveVideoFileThread编码线程 | `QList<BufferDataNode*>` | QMutex(视频/音频各一把) |
| 服务端任务处理 | epoll事件循环(recv_task) | 线程池worker线程 | 环形数组task_t[] | pthread_mutex + 两个pthread_cond |

三处的核心思想完全一致：**生产快慢不一致的两个环节不能直接耦合，用一个带锁的队列作缓冲区解耦**，队列满/空时用条件变量让对应一方等待，避免忙轮询浪费 CPU。理解了其中一处，另外两处基本是同一套思路换了个应用场景。

**背压（流控）也是这个模式里配套要处理的问题**：`videoplayer.cpp` 的读线程会检查队列大小，超过阈值（视频约12.7MB，音频约10MB）就 `SDL_Delay(10)` 暂停读，这是用空间换时间的经典手法。项目上传文件那条链路里目前**没有**做对应的背压处理（详见项目开发逐字稿第七节的分析），是一个已知的改进点。

## 七、渲染：为什么用 OpenGL 而不是 QPainter

`opengl/myopenglwidget.cpp` 自己实现了一个基于 `QOpenGLWidget` 的渲染控件，没有用 `QPainter::drawImage` 或者 Qt 自带的 `QVideoWidget`。核心渲染逻辑：

```cpp
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA, m_image.width(), m_image.height(),
             0, GL_BGRA, GL_UNSIGNED_BYTE, m_image.bits());   // 把RGB数据上传成GPU纹理
glBegin(GL_QUADS);
    glTexCoord2f(0, 1); glVertex2d(left, bottom);   // 用四个顶点画一个矩形贴图
    ...
glEnd();
```

**为什么不用 QPainter**：`QPainter` 每一帧都要 CPU 参与像素级的拷贝和合成，是软件渲染路径；OpenGL 把纹理上传给 GPU 之后，画面合成、缩放、混合都由显卡硬件加速完成，CPU 只需要做"把新一帧数据传上去"这一步。对视频这种高频率（每秒25次以上）持续刷新的场景，OpenGL 的效率优势非常明显，尤其在低性能设备上差距更大。

代码里还有个细节：`getImageScaledSize` 按 `Qt::KeepAspectRatio` 计算等比缩放后的尺寸，再换算成 OpenGL 归一化坐标系（`-1~1`）下的顶点位置，保证视频画面在窗口里始终保持原始宽高比、不会被拉伸变形，这是做视频播放控件时容易被忽略但体验上很重要的一个细节。

## 八、软解码 vs 硬解码

- **软解码/软编码**：用 CPU 跑解码/编码运算，兼容性好、依赖少，但 CPU 占用高。
- **硬解码/硬编码**：调用 GPU 或专用硬件芯片（Windows的D3D11VA、Linux的VAAPI/VDPAU，编码侧如NVIDIA的NVENC），速度快、CPU占用低，但依赖具体硬件和驱动支持。

**项目用的是软解码+软编码**：`avcodec_find_decoder`/`avcodec_find_encoder` 没有指定任何硬件加速的 codec 名称，FFmpeg 默认返回的就是软件实现；编码侧用 `c->thread_count = 4` 开多线程软编码来提升速度，而不是接入硬件编码器。这是一个明确的技术选型取舍：软解码/软编码不需要处理"不同显卡驱动兼容性""编译时是否链接了硬件加速库"这类环境依赖问题，让项目在任意一台装好 FFmpeg 库的机器上都能跑，代价是 CPU 占用比硬解码方案高不少——对于学习/练手项目，"哪都能跑"比"性能最优"更重要。

## 九、RTMP 推拉流：容器格式如何决定协议选型

### 9.1 为什么 FLV 容器天然适合 RTMP

RTMP（Real Time Messaging Protocol）设计之初就是配合 FLV 格式传输的，FLV 的 tag 结构和 RTMP 的 message 结构可以近乎无缝对应，这是历史上 Adobe 同时设计这两者留下的结果。项目里编码时选 FLV 容器（`savevideofilethread.cpp:419`），代码注释直接写着"为了未来推流rtmp（flv）"——**容器格式的选型在最开始写录制功能的时候就已经为后续的直播功能埋好了伏笔**，这是一个体现"技术选型要考虑未来扩展性"的例子。

### 9.2 rtmp:// 协议在 FFmpeg 里是怎么工作的

`rtmp://` 是 FFmpeg 内置的原生协议实现（`libavformat/rtmpproto.c`），编译时不需要额外链接 `librtmp` 外部库（只有 `rtmpe`/`rtmps`/`rtmpt` 这些加密/隧道变体才依赖外部库）。播放器和推流端调用的是同一套 API：

```cpp
avformat_open_input(&pFormatCtx, "rtmp://ip:1935/videotest/streamKey", NULL, NULL); // 拉流(读)
avformat_alloc_output_context2(&oc, NULL, "flv", "rtmp://ip:1935/videotest/streamKey"); // 推流(写)
avio_open(&oc->pb, url, AVIO_FLAG_WRITE);
```

`AVFormatContext` 是"已打开的媒体源/目标"的统一抽象，不管是本地文件、HTTP、还是 RTMP 网络流，上层 API 调用方式完全一致——这是 FFmpeg 架构设计上很值得学习的一点：把"数据从哪来/到哪去"这件事完全封装进协议层（`AVIOContext`），业务代码不需要为每种数据源写不同的读写逻辑。

项目文档里专门提到，拉流（读）和推流（写）虽然共用同一个协议模块，但走的是两条不同的代码路径，**上线前专门做了一次命令行实测**（`ffmpeg -re -i xxx.mp4 -c copy -f flv rtmp://ip:1935/videotest/test1` 推流 + `ffplay` 拉流验证），确认当前项目自带的 FFmpeg 4.2.2 预编译库两条路径都支持，才敢往正式代码里接——这是"没有实测验证过的路径，不要想当然认为能用"这条工程原则的具体体现。

### 9.3 服务端在直播链路里的角色边界

MediaServer 只负责信令（谁在播、streamKey是什么、状态是否进行中），完全不接触媒体流数据；真正的推流接收、多路分发、GOP缓存补关键帧全部交给 nginx-rtmp 这类专业组件。这个边界划分是"专业的事交给专业的组件"的取舍——服务端自己实现一遍音视频转发逻辑，工作量大且容易有bug，性价比不高。

## 十、这些知识点连起来看：一帧画面/一段声音的完整旅程

**录制/推流一帧视频的完整旅程**：
```
摄像头 → RGB24(OpenCV采集)
       → sws_scale转YUV420P(picinpic_read.cpp)
       → 队列缓冲(videoDataQuene_Input，生产者消费者解耦)
       → 编码线程按pts顺序取出(av_compare_ts比较音视频时序)
       → H.264编码(avcodec_send_frame/avcodec_receive_packet, superfast+zerolatency)
       → 时间戳换算到流的time_base(av_packet_rescale_ts)
       → FLV容器交错写入(av_interleaved_write_frame)
       → 本地文件 或 avio_open("rtmp://...")推流出去
```

**播放/拉流一帧视频的完整旅程**：
```
本地文件 或 rtmp://拉流 → av_read_frame读出AVPacket
       → 按stream_index分发进videoq(PacketQueue，生产者消费者)
       → video_thread非阻塞取包
       → avcodec_decode_video2解码得到YUV帧(pFrame)
       → synchronize_video维护video_clock
       → 与audio_clock比较，video_pts>audio_pts则SDL_Delay等待
       → sws_scale转RGB32
       → QImage.copy()深拷贝
       → 信号发给UI线程
       → MyOpenGLWidget上传纹理，glBegin(GL_QUADS)绘制显示
```

把这两条链路对照着看，会发现编码和解码几乎是完全对称的镜像流程，中间"YUV420P存储态"和"时间戳同步"是两条链路共享的核心概念——这也是为什么本合集把 YUV/RGB、时间戳同步单独拿出来作为独立章节，而不是分散写在"编码"和"解码"两节里各写一遍：它们是连接两条链路的公共知识点。

## 十一、Qt 在项目里承担的角色

前面十节讲的都是音视频本身的知识，但项目的客户端是用 Qt 搭的框架，音视频链路能跑起来、能跨线程流转、能显示到界面上，背后全靠 Qt 的几套机制在支撑。这一节单独讲清楚 Qt 具体做了什么，重点讲信号槽——因为它是这个项目里线程间通信的唯一手段，音视频数据从采集线程、编码线程、解码线程流向 UI 线程，全靠它。

### 11.1 Qt 在项目里做的六件事

1. **GUI 框架**：所有窗口（`QDialog`）、控件、`.ui` 文件都是 Qt Designer 设计生成的。
2. **多线程模型**：`QThread` 承载了采集线程（`PicInPic_Read`）、编码线程（`SaveVideoFileThread`）、解码播放线程（`VideoPlayer`），以及上传工作线程（`UploadWork` + `moveToThread`）。
3. **信号槽机制**：贯穿全项目的对象间/线程间通信方式，见下文 11.2~11.6。
4. **音频采集**：`QAudioInput`/`QAudioFormat`——这是音视频链路里唯一没有自己手写、直接用 Qt 封装的环节（`audio_read.cpp`），因为采集本身不是项目要理解的核心，省下精力放在"采集出来的数据怎么转格式给编码器"这一步上。
5. **OpenGL 集成**：`QOpenGLWidget` + `QOpenGLFunctions` 承载视频渲染（`myopenglwidget.cpp`），细节见第七节。
6. **辅助工具类**：`QImage`（图像容器，贯穿整条视频链路的数据载体）、`QMutex`（编码线程里保护视频/音频队列）、`QTimer`（音频采集定时轮询、UI进度定时刷新）、`QFile`/`QDir`（文件读写）、`QProcess`（拉起外部 ffmpeg 命令行生成 GIF 缩略图）。

### 11.2 为什么用信号槽，而不是手写锁+条件变量

如果不用信号槽，线程间通信的常规做法是：共享变量 + 互斥锁 + 条件变量，手动管理"谁写谁读、什么时候通知对方"。项目里的服务端（`Thread_pool.cpp`，纯 C++ 没有 Qt）就是这么干的，能看到大量手写的 `pthread_mutex_lock/pthread_cond_wait/pthread_cond_signal`。

客户端选信号槽，本质上是把这套"加锁-等待-唤醒"的机制**框架化**了：发送方只管 `emit`，不用关心接收方在哪个线程、需不需要加锁，Qt 内部自动处理跨线程投递。这是信号槽相比手写线程通信最大的价值——**把"线程安全"这件事从业务代码里抽走，交给框架保证**。

### 11.3 三种连接方式，项目里各自对应什么场景

`connect()` 的第五个参数决定了槽函数怎么被调用，这是信号槽机制真正的核心。

**① `Qt::AutoConnection`（默认，项目里绝大多数 connect 都没写第五个参数）**

```cpp
connect(m_player, SIGNAL(SIG_getOneImage(QImage)), this, SLOT(slot_setOneImage(QImage)));
```

Qt 在**运行时**判断发送者和接收者是否在同一线程：同线程 → 退化成 `DirectConnection`，相当于直接函数调用，同步执行；跨线程 → 自动变成 `QueuedConnection`，把这次调用打包成一个事件，投递到接收方所在线程的事件队列里，等接收方线程的事件循环转到才会执行。

典型跨线程例子：视频解码线程（SDL 线程，非 Qt 线程）通过 `SendGetOneImage` 把解码好的 `QImage` 发给主线程的 `PlayerDialog::slot_setOneImage` 更新 UI——这一步跨线程，自动变成 `QueuedConnection`，`QImage` 对象被**拷贝**一份塞进事件队列（这正是第二节讲过的"必须 `.copy()` 深拷贝"的原因之一：不拷贝的话队列里存的是指向下一帧会被覆盖的内存的视图）。这也保证了 UI 控件只在主线程被访问——Qt 规定 GUI 控件不能跨线程直接操作，`QueuedConnection` 天然满足这个约束。

**② `Qt::DirectConnection`（同线程下 AutoConnection 退化成的效果，被刻意利用来做隐式同步）**

同线程时 `emit` 是同步调用，槽函数跑完之后 `emit` 那一行才返回。这个特性在直播模块的信号转发上被刻意利用了一次：

```cpp
void OnlineDialog::slot_ReadyData(unsigned int lSendIP, char *buf, int nlen)
{
    switch(nType) {
        case _DEF_PACK_LIVE_START_RS:
        case _DEF_PACK_LIVE_LIST_RS:
            emit SIG_LivePacket(buf, nlen);   // LiveDialog 只读，不 delete
        break;
    }
    delete[] buf;   // 必须等 LiveDialog 处理完 buf 才能执行到这一行
}
```

`OnlineDialog` 和 `LiveDialog` 都在主线程，`emit SIG_LivePacket(buf,nlen)` 是同步调用，会先跑完 `LiveDialog::slot_handleLivePacket` 全部逻辑才返回，然后才走到 `delete[] buf`。这保证了 `LiveDialog` 用 `buf` 时这块内存一定还活着，不会出现 use-after-free——**这里没有用任何锁，完全靠"同线程信号槽是同步调用"这个机制特性来保证内存安全**。

但这个设计是有前提假设的：一旦哪天有人把 `LiveDialog` 挪到别的线程，`emit` 会自动变成异步的 `QueuedConnection`，"用完才删"的保证就会悄悄失效，变成潜在的 use-after-free，而且编译期不会报错，只会在运行时随机崩溃。这是信号槽虽然帮你处理了跨线程投递、但**不同连接方式下内存/时序假设不同**、不能想当然的一个真实例子。

**③ `Qt::BlockingQueuedConnection`（项目里唯一一处显式指定，专门解决"跨线程调用并同步等结果"）**

```cpp
// picinpic_read.cpp
connect(this, SIGNAL(SIG_getDeskImg()), this, SLOT(slot_getDeskImg()), Qt::BlockingQueuedConnection);
```

这种连接方式像 `QueuedConnection` 一样把调用投递给接收方线程处理，但**发送方会阻塞等待，直到槽函数执行完才返回**，行为上等价于跨线程的同步函数调用。

用它的原因：`PicInPic_Read` 是独立的采集线程（`run()` 里跑），但 `slot_getDeskImg()`（抓桌面截图 `QScreen::grabWindow`）涉及窗口系统操作，必须在**主线程**执行（Qt 的 GUI 相关调用只能在创建它们的主线程里调，不是线程安全的）。采集线程不能直接调这个槽（那样就是跨线程直接调用），用 `emit + BlockingQueuedConnection`：采集线程发出信号 → 投递给主线程执行 `slot_getDeskImg` → 采集线程原地阻塞等着 → 主线程执行完把结果（`m_deskImg`）填好 → 采集线程被唤醒继续用这个结果。这是"必须跨线程调用、又要求同步拿到返回值"这个需求的标准解法，比自己手写条件变量实现同样的效果简洁得多。

### 11.4 moveToThread：让整个对象的槽函数运行在另一个线程

信号槽解决的是"调用"的问题，但要让一个对象的槽函数真正运行在另一个线程，需要 `moveToThread`：

```cpp
// onlinedialog.cpp
m_uploadWorker = new UploadWork;
m_uploadthread = new QThread;
connect(m_uploadDialog, SIGNAL(SIG_UploadFile(QString,QString,Hobby)),
        m_uploadWorker, SLOT(slot_UploadFile(QString,QString,Hobby)));
m_uploadWorker->moveToThread(m_uploadthread);
m_uploadthread->start();
```

`UploadWork` 是个普通 `QObject`（不是 `QThread` 子类），`moveToThread` 把它的"所属线程"从主线程切换成 `m_uploadthread`。切换之后，任何对它槽函数的跨线程信号连接自动走 `QueuedConnection`，槽函数真正在 `m_uploadthread` 里执行——上传视频这种耗时的网络 IO（整个文件分块发送），不会卡住主线程 UI。

项目里另有一种线程模型：`PicInPic_Read`/`SaveVideoFileThread`/`VideoPlayer` 直接继承 `QThread` 重写 `run()`。两种模式怎么选是按对象职责性质定的：
- **继承 QThread 重写 run()**：适合"这个对象本身就是一个独立的执行流程"，比如采集、编码、解码，`run()` 里是一个完整的循环体，自己驱动自己。
- **普通 QObject + moveToThread**：适合"这个对象只是想让它的槽函数跑在别的线程"，本身没有独立主循环，靠外部信号驱动它干活。

项目里两种都用到了，是按对象职责选对应模型，不是随意混用。

### 11.5 自定义结构体跨线程传参：qRegisterMetaType

```cpp
// onlinedialog.cpp / uploaddialog.cpp / logindialog.cpp 构造函数开头都有
qRegisterMetaType<Hobby>("Hobby");
```

`Hobby` 是自定义结构体（8 个兴趣标签）：

```cpp
struct Hobby{
    char food; char funny; char ennegy; char dance;
    char music; char video; char outside; char edu;
};
```

信号槽走 `QueuedConnection`（跨线程）时，参数要被拷贝塞进事件队列排队，这要求参数类型支持"复制+存储"。Qt 内置类型（`int`/`QString`等）天然支持，但**自定义结构体默认不被 Qt 的元对象系统认识**，必须显式 `qRegisterMetaType` 注册，Qt 才知道怎么在队列里安全拷贝/传递这个类型。`SIG_registerCommit(QString,QString,Hobby)` 这个信号涉及跨线程投递（比如给 `UploadWork` 那条线程），`Hobby` 参数必须提前注册，不然运行时会报"无法排队自定义类型参数"的警告，槽函数根本不会被调用——这是信号槽机制里一个常见的坑，项目里三处都在构造函数最开头注册，说明这个坑已经被踩过并且被记住了。

### 11.6 signals/slots 的访问权限用法

项目里 `public slots` 和 `private slots` 用法是有讲究的：

```cpp
// livedialog.h
public slots:
    void setUserInfo(int userId, QString userName);   // 外部对象需要连接/调用的槽，开放
private slots:
    void on_pb_startLive_clicked();                    // Qt Designer自动关联的UI槽，无需外部访问
```

`public slots` 一般是"设计给外部对象连接调用的接口"，比如 `setUserInfo` 是 `PlayerDialog` 连接 `OnlineDialog::SIG_LoginSuccess` 时要用的槽，必须公开；`private slots` 大多是 `on_控件名_clicked()` 这类槽——Qt 通过命名约定（`on_对象名_信号名`）自动 `connect`，不需要手写 `connect` 语句，这类槽只服务当前对象内部的 UI 交互，不需要暴露给外部，所以设成 `private`。

### 11.7 小结：信号槽在这个项目里到底解决了什么

| 用途 | 例子 | 连接方式 |
|---|---|---|
| 解码线程→UI线程 传画面 | `VideoPlayer::SIG_getOneImage` → `slot_setOneImage` | AutoConnection（自动变Queued） |
| 同线程对象间转发数据，依赖同步语义保证内存安全 | `OnlineDialog::SIG_LivePacket` → `LiveDialog` | AutoConnection（自动变Direct） |
| 采集线程需要在主线程执行GUI操作，并同步等结果 | `SIG_getDeskImg` → `slot_getDeskImg` | 显式BlockingQueuedConnection |
| 把耗时任务丢到独立线程执行，不卡UI | `UploadWork` + moveToThread | AutoConnection（自动变Queued） |
| 自定义结构体跨线程传递 | `Hobby` 结构体 | 需要先qRegisterMetaType |

这套机制换来的好处是：**业务代码里几乎看不到手写的锁**（对比服务端 `Thread_pool.cpp` 里大量的 `pthread_mutex_lock/unlock`），线程安全这件事被下沉到 Qt 框架层处理。但代价也要说清楚——这种"自动"是有前提假设的（线程模型不变），一旦对象的线程归属发生变化（比如误把某个对象 `moveToThread` 到别处），原本靠 `DirectConnection` 同步语义保证的内存安全假设就会悄悄失效，而且不会有编译错误提示，只会在运行时才暴露成随机崩溃。这是用信号槽简化并发编程要付出的隐性代价，理解这一点，才算真正吃透了这套机制，而不是停留在"能用就行"。

# MediaPlay 音视频编码功能讲解

> 基于项目代码：Qt5 + FFmpeg 4.2.2，用人话讲清楚整个编码流程。

---

## 先搞清楚几个基本概念

在看流程之前，先把几个经常混淆的概念说清楚：

**编码（Encode）**：把原始的、体积巨大的音视频数据，压缩成小文件存起来。比如把摄像头拍的 RGB 图像压成 H.264。

**解码（Decode）**：反过来，把压缩好的小文件还原成可以显示/播放的数据。

**PCM**：麦克风采集到的原始音频，就是一堆数字，未经压缩，体积大。

**YUV420P**：摄像头采集的画面通常是 RGB 格式，但视频编码器（H.264）不吃 RGB，它吃 YUV 格式。所以采集之后要先转格式。

**AAC / H.264**：分别是音频和视频最常用的压缩格式，本项目就用这两种。

**PTS（Presentation Time Stamp）**：每一帧画面/声音都有一个时间戳，用来告诉播放器"这帧应该在第几秒播"。音视频同步靠的就是这个。

---

## 整体架构：四个独立线程协作

```
主线程 (UI界面)
    │
    ├── PicInPic_Read 线程     → 负责采集摄像头/桌面画面，转成 YUV 格式
    │
    ├── Audio_Read 对象        → 负责采集麦克风音频，转成 FLTP 格式
    │
    └── SaveVideoFileThread    → 核心编码引擎，从两个队列取数据，
                                 H.264编码视频 + AAC编码音频，
                                 混合写入 FLV/MP4 文件
```

采集和编码是分开的。采集线程不停地往队列里塞数据，编码线程不停地从队列里取数据编码。这样互不干扰，不会因为编码慢了就卡住采集。

---

## 音频编码流程（从麦克风到 AAC）

### 第一步：采集原始 PCM 音频

代码位置：`audio_read.cpp`

```
麦克风 → Qt 的 QAudioInput → 读取 PCM 数据
```

参数：
- 格式：S16（有符号 16 位整数），采样率 44100Hz，双声道
- 每次读取 4096 字节（约 20ms 的音频）

### 第二步：格式转换 S16 → FLTP

麦克风吐出来的是 S16 格式（整数），但 AAC 编码器要求 FLTP 格式（浮点数，左右声道分开存放）。

用 FFmpeg 的 `SwrContext`（重采样器）来转：

```
PCM S16（左右声道交错）  →  SwrContext  →  FLTP（左声道一段，右声道一段）
```

转完之后，通过信号（Qt 的 Signal）把数据发给编码线程的队列。

### 第三步：编码线程从队列取数据，AAC 编码

代码位置：`savevideofilethread.cpp` 的 `write_audio_frame()`

```
从 audioDataQueue 取出 FLTP 数据
↓
填入 AVFrame（音频帧结构体）
↓
设置 PTS 时间戳（累加采样点数，保证时间连续）
↓
avcodec_send_frame()   → 把帧塞给编码器
avcodec_receive_packet() → 从编码器拿出压缩好的 AAC 数据包
↓
写入文件
```

AAC 编码器配置：64kbps 码率，44100Hz，双声道。

---

## 视频编码流程（从摄像头到 H.264）

### 第一步：采集画面

代码位置：`picinpic_read.cpp`

- 摄像头：用 OpenCV 的 `cap.read()` 读一帧
- 桌面截图：Qt 截屏
- 两路画面可以叠加（画中画效果）

采集到的格式是 RGB24（每个像素 R、G、B 三个字节）。

### 第二步：RGB24 → YUV420P 格式转换

H.264 编码器只认 YUV420P，不认 RGB，所以必须先转格式。

用 FFmpeg 的 `SwsContext`（图像缩放/转换器）来转：

```
RGB24 图像
↓
sws_scale()
↓
YUV420P（Y分量：亮度，U/V分量：色度）
```

YUV420P 的大小 = 宽 × 高 × 1.5 字节（相比 RGB24 的 宽×高×3，体积小了一半）。

转完之后也是发信号给编码线程的队列。

### 第三步：编码线程从队列取数据，H.264 编码

代码位置：`savevideofilethread.cpp` 的 `write_video_frame()`

```
根据当前时间从 videoDataQueue 取对应帧
（如果没有，就用上一帧重复，避免卡顿）
↓
填入 AVFrame（视频帧结构体）
↓
设置 PTS（next_pts 自增）
↓
avcodec_send_frame()    → 把帧塞给 H.264 编码器
avcodec_receive_packet() → 拿出压缩好的 H.264 数据包
↓
写入文件
```

H.264 编码器配置：
- preset = `superfast`（编码速度优先，适合实时场景）
- tune = `zerolatency`（零延迟，不缓冲帧）
- GOP = 12（每 12 帧一个关键帧 I-Frame）
- 线程数 = 4（多核并行编码）

---

## 音视频同步：谁落后谁先编

代码位置：`savevideofilethread.cpp` 的 `run()` 主循环

音频和视频都在往文件里写，如果节奏不对，会出现"嘴对不上"的问题。

解决方案：用 PTS 比较，**谁的时间戳更靠前，就先编谁**。

```cpp
// 伪代码
while (还有数据) {
    if (视频下一帧的时间 <= 音频下一帧的时间) {
        编码一帧视频;
    } else {
        编码一帧音频;
    }
}
```

用的是 FFmpeg 的 `av_compare_ts()` 函数来比较不同时间基的时间戳。

## 解码播放流程（反过来）

代码位置：`videoplayer.cpp`

```
读文件 av_read_frame()
↓
分包 → 视频包放 videoQueue，音频包放 audioQueue
↓
视频解码线程：avcodec_decode_video2() → YUV → sws_scale() → RGB → 显示
音频解码线程：avcodec_decode_audio4() → PCM → swr_convert() → SDL 播放

同步：视频帧的 PTS > 音频时钟时，视频等一等（sleep）
```

---

## 数据流一图流

```
【音频路径】
麦克风 → QAudioInput → PCM(S16) → swr_convert → FLTP → audioQueue
                                                            ↓
                                              编码线程 → AAC → 文件

【视频路径】
摄像头/桌面 → OpenCV/Qt → RGB24 → sws_scale → YUV420P → videoQueue
                                                              ↓
                                                编码线程 → H.264 → 文件

【文件输出】
H.264 + AAC → av_interleaved_write_frame() → FLV/MP4 文件
```

# 面试可能被问到的问题（音视频编码方向）

---

## 基础概念类

**Q1：PCM 是什么？为什么要转成 FLTP 才能 AAC 编码？**

PCM（Pulse Code Modulation，脉冲编码调制）是未压缩的原始音频，就是把声音的振幅按固定频率采样成数字。S16 是每个采样点用一个有符号 16 位整数表示。

AAC 编码器内部运算是基于浮点数的，它要求输入是 `AV_SAMPLE_FMT_FLTP`（Float Planar），即每个声道的数据单独存一段，用 float 类型。所以需要用 `SwrContext` 做格式转换。

---

**Q2：YUV420P 是什么，为什么视频编码用 YUV 而不用 RGB？**

YUV 是一种将亮度（Y）和色度（U、V）分离的颜色模型。420P 的"420"表示色度（U/V）在水平和垂直方向都是 2x 降采样——即每 4 个 Y 像素共用 1 个 U 和 1 个 V。

用 YUV 的原因：
1. 人眼对亮度变化比色度更敏感，降采样色度对主观画质影响小
2. 体积只有 RGB24 的一半（宽×高×1.5 vs 宽×高×3）
3. H.264/H.265 等编码标准基于 YUV 设计，这是业界标准

---

**Q3：I 帧、P 帧、B 帧分别是什么？**

- **I 帧（关键帧）**：完整存储一帧画面，不依赖其他帧，可以独立解码。H.264 一般每隔几十帧插一个 I 帧（本项目 GOP=12 即每 12 帧一个 I 帧）。
- **P 帧（预测帧）**：只存与前一帧的差异，体积小，但解码需要依赖前面的帧。
- **B 帧（双向预测帧）**：参考前后两帧做差，压缩率最高，但延迟大。本项目用的是 `zerolatency` 模式，一般会禁用 B 帧。

---

**Q4：PTS 和 DTS 的区别是什么？**

- **PTS（Presentation Time Stamp）**：显示时间戳，这帧应该在什么时间显示给用户。
- **DTS（Decoding Time Stamp）**：解码时间戳，这帧应该在什么时间解码。

有 B 帧时，解码顺序和显示顺序不同（B 帧要等后面的帧先解码才能解自己），所以 DTS ≠ PTS。没有 B 帧时两者相等。

---

**Q5：码率（bit rate）和帧率（frame rate）的区别？**

- **帧率（fps）**：每秒播放多少帧画面，影响流畅度。本项目是 25fps。
- **码率（bps）**：每秒输出多少 bit 的压缩数据，影响文件大小和画质。本项目视频码率可配置，音频 64kbps。

两者关系：帧率高，编码器需要处理的帧更多，在同等码率下每帧分到的 bit 数更少，画质下降。

## 流程机制类

**Q6：音视频同步是怎么实现的？**

本项目编码端：在编码主循环中，用 `av_compare_ts()` 比较音频流和视频流各自的下一帧 PTS，谁的时间更靠前就先编谁，保证写入文件的数据时间上是交错对齐的。

播放端：维护一个音频时钟（不断推进），视频线程解码每帧后，如果视频 PTS 超过了音频时钟，就 sleep 等一等，实现视频对齐音频。

**常见的三种同步策略**：
1. 以音频为基准（最常用，因为人耳对声音延迟更敏感）
2. 以视频为基准
3. 以外部时钟为基准

---

**Q7：为什么要用队列（Queue）来连接采集和编码线程？**

典型的生产者-消费者模式。

原因：
1. 采集速度和编码速度可能不一致（编码有时快有时慢）
2. 不能让采集线程等编码，也不能让编码线程等采集
3. 队列作为缓冲，解耦两个线程，各自以最优速度运行
4. 需要加锁（mutex + 条件变量）保证线程安全

本项目用 SDL_mutex 和 SDL_cond 实现线程安全队列。

---

**Q8：avcodec_send_frame 和 avcodec_receive_packet 为什么是分开的？**

这是 FFmpeg 3.x 引入的新 API（取代旧的 `avcodec_encode_video2`）。

分离的好处：
- 编码器内部可以缓冲多帧（比如 lookahead 优化、B 帧重排），不是一帧进一帧出
- send 和 receive 解耦：可以连续 send 多帧，然后一次性 receive 多个包
- 返回 `EAGAIN` 表示"还没准备好输出"，这是正常状态，要继续 send 更多帧

---

**Q9：H.264 的 preset 和 tune 参数是什么意思？**

**preset**（预设速度）：从 `ultrafast` 到 `veryslow`，越慢压缩率越高、文件越小，但 CPU 占用越大。
- 本项目用 `superfast`，适合实时编码，速度优先。

**tune**（场景调优）：
- `zerolatency`：禁用 lookahead 和 B 帧，编码器不缓冲帧，适合直播/实时传输。
- `film`：针对电影内容优化。
- `animation`：针对动画内容优化。

---

**Q10：SwsContext 和 SwrContext 分别用来做什么？**

- **SwsContext**（Software Scaling Context）：视频格式转换和缩放。比如 RGB24→YUV420P，或者把 1080p 缩放到 720p。用 `sws_scale()` 执行。
- **SwrContext**（Software Resampling Context）：音频重采样和格式转换。比如 S16→FLTP，或者把 48000Hz 转成 44100Hz。用 `swr_convert()` 执行。

---

## 进阶/深度类

**Q11：GOP 大小对编码有什么影响？**

GOP（Group of Pictures）是两个相邻 I 帧之间的帧数。

- **GOP 大**（比如 250）：I 帧少，文件小，但 seek（拖进度条）时响应慢，因为要找到最近的 I 帧才能开始解码。
- **GOP 小**（比如 12）：I 帧多，文件稍大，但 seek 更快，适合录屏、会议等需要精确定位的场景。
- **直播场景**：GOP 通常设 1~3 秒，保证断线重连后快速恢复画面。

本项目 GOP=12，帧率 25fps，意味着每 0.48 秒一个关键帧。

---

**Q12：为什么音频帧大小是 1024 个采样点？**

AAC 编码器的一个工作单元固定是 1024 个采样点（这是 AAC 标准规定的，基于 MDCT 变换的块大小）。

所以：
- 采集端要凑够 1024 个采样点才能给编码器
- 在 44100Hz 采样率下，1024 个点约等于 23.2ms 的音频
- `c->frame_size` 就是编码器告诉你"我一次需要多少采样点"

---

**Q13：av_interleaved_write_frame 和 av_write_frame 的区别？**

- `av_write_frame()`：直接写，不管时间顺序。
- `av_interleaved_write_frame()`：内部会做排序缓冲，保证写入文件的音视频包按 DTS 时间顺序交错排列（interleaved）。

对于音视频混流文件（MP4/FLV），必须用 interleaved 版本，否则播放器解封装时会出问题。

---

**Q14：如果编码线程处理不过来，队列一直积压怎么办？**

常见策略：
1. **丢帧**：当队列超过阈值，直接丢弃最老的帧（视频场景常用，牺牲帧率换实时性）
2. **降质量**：动态降低分辨率或码率
3. **限速**：让采集端慢下来，适合非实时场景

本项目在视频没有对应帧时会复用上一帧（减少队列压力），这是一种简单的自适应策略。

---

**Q15：时间基（time_base）是什么，为什么要做时间戳转换？**

时间基是时间戳的"单位"。比如 `time_base = {1, 44100}` 表示每个时间单位是 1/44100 秒。

不同组件有不同的时间基：
- 音频编码器：`{1, sample_rate}`（以采样点为单位）
- 视频编码器：`{1, frame_rate}`（以帧为单位）
- 输出流：可能是 `{1, 90000}`（MPEG 标准时间基）

写入文件前必须用 `av_packet_rescale_ts()` 把 packet 的时间戳从编码器时间基转换成流的时间基，否则播放时时间对不上。

---

**Q16：直播推流和录制文件在编码上有什么区别？**

| 对比项 | 录制文件 | 直播推流 |
|--------|----------|----------|
| 延迟要求 | 无要求 | 越低越好（<3s） |
| preset | slow/medium，画质优先 | superfast，速度优先 |
| B 帧 | 可以用，压缩率高 | 禁用（zerolatency），减少延迟 |
| GOP | 可以大 | 1~3秒，方便断线重连 |
| 输出 | MP4/MKV，可 seek | RTMP/FLV，流式 |
| 尾部处理 | 需要 write_trailer 写索引 | 不需要，持续推 |
